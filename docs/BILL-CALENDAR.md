# ปฏิทินบิลและ LINE Flex แจ้งเตือน

หน้า `/app/settings/bills` แตะวันเพื่อดูหรือเพิ่มบิล เลือกครั้งเดียว/ทุกเดือน ตรวจชื่อ ยอด และวันก่อนยืนยัน การเพิ่มบิลสร้างแผนกันเงินตามรอบ ไม่สร้างรายจ่ายจนยืนยันจ่ายจริงผ่าน flow แผนเดิม บิลเก่าที่ไม่เคยตั้งวันแสดงแยกไว้โดยไม่เดาวันให้

เปิดการเตือนรายบิลโดยผู้ใช้ เริ่มส่ง **09:00 ตามเวลาไทย ล่วงหน้า 3 วันและวันครบกำหนด** เฉพาะสถานะ reserved ในรอบ active ไม่ส่งหลัง 22:00 หรือย้อนส่งวันแจ้งเตือนที่พ้นไปแล้ว Flex มีชื่อ ยอด วันที่ และปุ่มดูบิล/จัดการเตือน การเปิดการ์ดยังไม่ยืนยันว่าจ่าย ต้องเพิ่มเพื่อน OA และรับข้อความได้

รายเดือนยึดวันที่เริ่ม: 31 มกราคม → 28/29 กุมภาพันธ์ → 31 มีนาคม แผนจริงสร้างผ่านเดือนถัดไปหรือเดือนวันรับเงินที่ไกลกว่า สร้างต่อเมื่อเปิดรอบเงินหรือขยายวันรับเงิน แม้ปิดส่ง LINE; worker sync เพิ่มด้วย วันที่เกินช่วงแผนจริงระบุเป็นรอบที่จะถึง ไม่ใช่รายจ่ายใหม่ ไม่มีการย้อนสร้างเดือนเก่าทั้งหมดที่ไม่ได้ใช้

หยุดตารางบิลยกเลิกบิลตั้งแต่วันนี้ที่ยังไม่จ่าย เก็บย้อนหลัง/ที่จ่ายแล้วไว้ ยกเลิกบิลรอบเดียวไม่หยุดรายเดือนถัดไป ชื่อ/ยอดตารางเดิมยังแก้ไม่ได้ ให้หยุดแล้วสร้างใหม่โดยตรวจยอดค้างเดิมก่อน

## API

- `GET /api/bills`: ตารางเปิดอยู่ของบัญชี LINE นี้ สูงสุด 50
- `POST /api/bills`: `Idempotency-Key` กับ `{title,amount,startsOn,repeat:"once"|"monthly",notify}` ยอดสตางค์ 1–10,000,000 วันที่ตั้งแต่วันนี้ไม่เกิน 1 ปี
- `PATCH /api/bills/:id`: `{notify:boolean}` หรือ `{stop:true}` ตรวจเจ้าของ
- Migration `20261116050000_bill_calendar.sql`: ตารางเปิด RLS ไม่มีสิทธิ์ anonymous; RPC เฉพาะ service role สร้างตาราง/แผนใน transaction เดียว มี unique occurrence และ delivery ledger ป้องกันซ้ำ

## เปิดใช้จริง

รอบนี้ apply migration เฉพาะ Supabase local ไม่ deploy ไม่แก้ฐานออนไลน์ และไม่ส่ง LINE จริง

1. Apply migrations ก่อนหน้ารวม `20261116050000_bill_calendar.sql` บนฐานเป้าหมายก่อน deploy เพราะ API แผนเลือกคอลัมน์ `bill_schedule_id` ใหม่
2. ตั้ง `LINE_BILL_REMINDERS_ENABLED=1`, `LINE_CHANNEL_ACCESS_TOKEN`, `CRON_SECRET` บนเซิร์ฟเวอร์ ปิด flag หยุด push แต่ไม่หยุดบิลรายเดือน
3. Scheduler/orchestrator เรียก `POST /api/cron/bills` ด้วย `Authorization: Bearer <CRON_SECRET>` ทุก 5 นาที เริ่มส่งเมื่อถึง 09:00 ไทย
4. ผล `{enabled,sent,failed,processed,nextCursor,repeatPage}` อ่านไม่เกิน 10 บัญชี ใช้ 2 workers จำกัด 20 send attempts และเวลา 110 วินาที ถ้า `repeatPage=true` เรียกหน้าเดิมด้วย cursor เดิมต่อ แม้ `nextCursor=null`; ถ้า false และ `nextCursor` มีค่าให้ตามจนจบ อย่าเรียกเฉพาะหน้าแรก
5. ติดตาม `failed`; retry หลัง lease 2 นาที โดยรอบถัดไปเริ่มไล่หน้าแรกได้ ใช้ retry UUID เดิม จำกัด 3 attempts และ recheck opt-in/สถานะก่อนส่ง การตอบรับ LINE ไม่ยืนยันว่าผู้ใช้ได้รับจริง โดยเฉพาะเมื่อบล็อก OA [เอกสาร retry ของ LINE](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)

พรีวิว builder เดียวกับ runtime ที่ `/dev/line-flex`: “บิล: เตือนล่วงหน้า 3 วัน” และ “บิล: ครบกำหนดวันนี้” ปิดเส้นทางใน production และปุ่มพรีวิวไม่ส่งคำสั่ง

ทดสอบด้วย `npm test`, `npm run test:db`, `npm run lint`, `npm run typecheck`, `npm run build` LINE push เป็นค่าจำลอง ครอบคลุมสิ้นเดือน/ปีอธิกสุรทิน, retry ข้ามเที่ยงคืน, รอบใหม่เมื่อปิดเตือน, ยืนยันซ้ำ, จ่าย/ยกเลิก/ปิดเตือน, เวลาไทย, worker ซ้อน, stable retry UUID, แบ่งหน้า และเจ้าของข้อมูล
