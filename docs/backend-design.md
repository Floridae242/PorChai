# เอกสารออกแบบ Backend — พอใช้

ร่าง 11 พ.ย. 2569 · ผู้เขียน: พอ (Backend) · สถานะ: อนุมัติ 11 พ.ย. · แก้ 11 พ.ย.: ใช้ LIFF แทน MINI App ตาม tech stack ที่ทีมกำหนด · แก้ 11 พ.ย. ค่ำ: สูตรและตารางตาม Figma "Slides (สำหรับเพื่อน)" (เงินออม, ค่าจำเป็นต่อวัน, ซื้อได้ไม่เกิน, ปรับยอด, บิลจ่ายแยก, 4 หมวด)

**Tech stack (ทีมกำหนด):** LINE OA + Messaging API · LIFF · Next.js + TypeScript · Supabase PostgreSQL · AI API (ยังไม่เลือกเจ้า) · Vercel · Microsoft Clarity · ทดสอบด้วย Vitest (เครื่องมือตอนพัฒนา ไม่อยู่ในแอป)
ยึดขอบเขตจาก "สรุป Final สำหรับทีม 11 พ.ย." ครอบคลุมการ์ด 03 (สูตร), 05 (ข้อมูล), 06 (ตัวตน) และวางทางให้ชั้นถัดไป

## 1. เจตนา

นักศึกษาต้องเห็น **ตัวเลขเดียวที่เชื่อได้**: วันนี้ใช้ได้อีกเท่าไรโดยยังพอถึงวันรับเงิน ตัวเลขนี้ต้องตรงกันทุกทาง (แชต, หน้าจอ LIFF, การเตือน, AI) และห้ามผิดหรือหักซ้ำ เพราะถ้าผู้ใช้เจอยอดผิดครั้งเดียวก็เลิกเชื่อแอป

Backend จึงมีหน้าที่หลักสองอย่าง
1. **ตัวคำนวณเดียว** ที่ทุกทางเรียกใช้
2. **การบันทึกที่เกิดครั้งเดียวและเป็นของเจ้าของบัญชีเท่านั้น** (R01, R02)

## 2. เป้าหมาย / ไม่ทำ / ห้ามเกิด

**เป้าหมาย** (เรียงตามชั้น ทำชั้นล่างให้ผ่านเทสต์ก่อนขึ้นชั้นบน)

| ชั้น | สิ่งที่ใช้งานได้ |
|---|---|
| 0 | ตรวจตัวตน, ตารางข้อมูล, ตัวคำนวณพร้อมเทสต์ |
| 1 | จดผ่านแชตและฟอร์ม → ยืนยัน → บันทึกครั้งเดียว · ตั้งรอบเงิน · สรุป · แก้/ลบรายการ · ลองก่อนจ่าย · วางแผน/จ่ายแล้ว |
| 2 | เตือนจากพฤติกรรม |
| 3 | AI อ่านข้อความแชตและช่วยคิดก่อนจ่าย |
| 4 | OCR ใบเสร็จ |
| 5 | โปรร้าน + รหัสใช้สิทธิ์ |
| 6 | แต้มรายวัน + แลกของ |
| 7 | รายงานรวมให้ร้าน (ถ้าไม่ทัน ใช้ตัวเลขจำลองในสไลด์) |

**จุดตรวจ:** 13–14 พ.ย. ตรวจระบบรวม ไม่เลื่อน ถ้าชั้นไหนไม่เสร็จให้ตัดชั้นนั้นและชั้นที่สูงกว่า

**ไม่ทำรอบนี้:** เชื่อมธนาคาร, โอน/ล็อกเงินจริง, จดกลุ่ม, ระบบบัญชีร้านเต็มรูปแบบ, ต่ออายุสมาชิก

**ห้ามเกิด (แม้ระบบจะ "ทำงานได้")**
- AI หรือระบบบันทึกรายจ่ายเองโดยผู้ใช้ไม่ได้กดยืนยัน
- ตัวเลขเงินมาจาก AI แทนที่จะมาจากตัวคำนวณ
- ผู้ใช้ A เห็นหรือแก้ข้อมูลของ B ได้ แม้แก้รหัสในคำขอ
- ยอดติดลบแต่หน้าจอแสดงงบที่ดูเหมือนยังมีเงิน
- key หรือข้อมูลจริงหลุดขึ้น repo (repo เป็น public)

  - ลิงก์ `liff.line.me/<id>/<path>` เปิดหน้าแรกพร้อม `?liff.state=` ก่อน → `app/liff-state-redirect.tsx` ใน layout เรียก `liff.init()` ให้พาไปหน้านั้น

### ทำไมใช้ LIFF ไม่ใช้ LINE MINI App (ตัดสินใจ 11 พ.ย. · การ์ด 04)

อาจารย์ไม่กำหนดว่าต้องเป็น MINI App หรือ LIFF ทีมเลือก LIFF เพราะ

1. **MINI App แบบผ่านการรับรอง (Verified) ทีมขอไม่ได้:** ในไทยต้องอยู่ใต้ Certified Provider ที่ LINE ตรวจว่าเป็นองค์กรจริง (ยื่นผ่านฝ่ายขาย LINE ส่วนใหญ่สำหรับบริษัท) กลุ่มนักศึกษาไม่มีนิติบุคคล และการตรวจใช้ 1–2 สัปดาห์ ไม่ทันส่งมอบ 17–18 พ.ย. ([Submitting LINE MINI App](https://developers.line.biz/en/docs/line-mini-app/submit/submission-guide))
2. **แบบไม่ผ่านการรับรอง (Unverified) ไม่ได้อะไรเพิ่ม:** ฟีเจอร์พิเศษ (ค้นหาใน LINE, แท็บ Home, service message, หัวจอโชว์ชื่อแอป) มีเฉพาะ Verified ([Custom features](https://developers.line.biz/en/docs/line-mini-app/discover/custom-features/))
3. **LIFF ทำได้ครบที่พอใช้ต้องใช้:** เปิดจากแชต LINE OA, ใช้บัญชี LINE เดียวกับแชต (Provider เดียวกัน), ยืนยันตัวตนด้วย ID token · ทดสอบบนมือถือจริงผ่าน 11 พ.ย. 22:20 (`/dev/liff-check` 5/5)
4. **ย้ายได้ถ้าจำเป็น:** MINI App ใช้ LIFF SDK ตัวเดียวกัน ย้ายไป channel "PorChai MiniApp" (Unverified) ได้ในราว 1 ชม. โดยเปลี่ยน LIFF ID ใน `lib/liff/config.ts` และ `LINE_LOGIN_CHANNEL_ID` ไม่ต้องเขียนหน้าจอใหม่
- **Microsoft Clarity (ฝั่งหน้าจอ):** ต้องปิดบังยอดเงิน ชื่อรายการ และรายละเอียดรายจ่ายทุกจุด (NFR04) ก่อนเปิดให้ผู้ทดลองใช้
- วันที่และ "วันนี้" ใช้เวลาไทย `Asia/Bangkok` เสมอ

## 4. ภาพรวมระบบ

```
นักศึกษา ─┬─ แชต LINE OA ──► webhook (/api/line/webhook) ─┐
          └─ หน้าจอ LIFF (Next.js) ──────► /api/* ───────┤
                                                          ├─► บริการกลาง (lib/) ─► Supabase Postgres
ตัวตั้งเวลา (Supabase cron) ──► /api/cron/reminders ───────┘        │
                                                                    └─► LINE Messaging API (reply / push)
```

- โค้ดทั้งหมดอยู่ใน repo เดียว deploy บน Vercel
- หน้าจอเรียกข้อมูลผ่าน `/api/*` เท่านั้น ไม่ต่อฐานข้อมูลตรง
- ฐานข้อมูลเปิด RLS ทุกตารางและไม่มี policy ให้ anon เลย → มีแค่ server (service role key) ที่อ่านเขียนได้ การกรองตามเจ้าของบัญชีทำในโค้ด back ทุกคำสั่ง

## 5. หลักเงินและสูตร (การ์ด 03)

### คำศัพท์

| คำ | ความหมาย |
|---|---|
| เงินตั้งต้นของรอบ | ยอดเงินที่ผู้ใช้มีตอนตั้งรอบ พร้อมเวลาที่ยอดนั้นจริง (W5 "แก้เวลา") |
| ยอดอ้างอิง | ยอดที่ผู้ใช้บอกล่าสุด: เงินตั้งต้น หรือยอดจาก "ปรับยอด" ครั้งล่าสุด (ตาราง `balance_checks`) |
| เงินจริงตอนนี้ | ยอดอ้างอิง − รายจ่ายที่จด **หลัง** เวลาของยอดอ้างอิง และเป็นของวันนั้นหรือหลังจากนั้น (`balanceNow`) |
| เงินออม | หักตั้งแต่ต้นรอบ เลือกเป็น % ของเงินตั้งต้น (ปัดลงเป็นบาท) หรือกรอกเป็นบาท ไม่นับในงบใช้จ่าย |
| เงินเผื่อ (ฉุกเฉิน) | ยอดที่ผู้ใช้กันไว้ ไม่นำมาหารเป็นงบรายวัน |
| ยอดกันไว้ | บิลค้าง + แผนที่สถานะ "วางแผน" ที่ครบกำหนดไม่เกินวันรับเงิน (`reservedTotal`) · บิลจ่ายแล้ว/จ่ายแยก/ยกเลิก ไม่นับ · ครบกำหนดหลังวันรับเงิน = รอบหน้า (W8) |
| เงินใช้ได้ | เงินจริงตอนนี้ − เงินเผื่อ − เงินออม − ยอดกันไว้ |
| ค่าจำเป็นต่อวัน | ค่ากิน + ค่าเดินทางต่อวันที่ผู้ใช้ตั้ง (W7) |
| วันที่เหลือ | จำนวนวันจากวันนี้ (นับวันนี้) ถึงวันก่อนวันรับเงิน |

### สูตร

```
งบต่อวัน        = เงินใช้ได้ ณ ต้นวันนี้ ÷ วันที่เหลือ
วันนี้เหลือ      = งบต่อวัน − รายจ่ายวันนี้
เงินเหลือหลังค่าจำเป็น (spare) = เงินใช้ได้ ณ ต้นวันนี้ − ค่าจำเป็นต่อวัน × วันที่เหลือ   (ติดลบ = ขาดเท่านั้น)
ซื้อได้ไม่เกิน    = spare                                              (ไม่ต่ำกว่า 0)
ขาดค่าจำเป็นวันละ = ค่าจำเป็นต่อวัน − งบต่อวัน                         (ไม่ต่ำกว่า 0)
พรุ่งนี้ใช้ได้     = สูตรเดียวกัน โดยวันนี้ = พรุ่งนี้ และรายจ่ายวันนี้ = 0
```

"ณ ต้นวันนี้" หมายถึงไม่นับรายจ่ายของวันนี้ (คือเงินใช้ได้ตอนนี้ + รายจ่ายที่ `spent_on` = วันนี้) งบต่อวันจึงคงที่ตลอดวัน ผู้ใช้เห็นยอดลดลงตามที่จ่าย ไม่ใช่งบที่แกว่งทุกครั้งที่จด ส่วนแผน "วางแผน" ที่สร้างระหว่างวันมีผลทันที เพราะผู้ใช้ตั้งใจกันเงินนั้นแล้ว

**ค่าจำเป็นที่ยังไม่ตั้ง ≠ 0 (การ์ด 14):** ตัวเลขหลักคือ "ใช้ได้วันละ" (เงินใช้ได้ ÷ วัน) แสดงเสมอ ส่วน spare, ซื้อได้ไม่เกิน, ขาดค่าจำเป็นวันละ ต้องรู้ค่ากิน+ค่ารถก่อน ถ้ายังไม่ตั้ง (`essential_*_daily` เป็น null) ระบบตอบ `null` = ยังไม่รู้ หน้าจอ/แชต/AI ต้องถามค่ากินค่ารถก่อน ห้ามเดา 0 (จะกลายเป็นเอาเงินทั้งก้อนมาเป็นเงินซื้อเพิ่ม) · ตั้งเป็น 0 เองได้ถ้าผู้ใช้บอกว่าไม่มีค่าใช้จ่ายประจำ · ค่ากินกับค่ารถต้องตั้งพร้อมกัน (DB บังคับ)

"ซื้อได้ไม่เกิน" ใช้ฐานต้นวันเหมือนงบต่อวัน จึงคงที่ทั้งวัน (Figma W12: จดข้าว 45 แล้วยังเป็น 600) ตรงกับการลองจ่ายที่คิดจากฐานเดียวกัน

**ปรับยอด (กันหักซ้ำ R01):** ไม่เก็บยอดคงเหลือแบบวิ่ง แต่เก็บ "ยอดที่ผู้ใช้บอก + เวลาที่ยอดนั้นจริง" รายจ่ายที่จดก่อนเวลานั้น หรือเป็นของวันก่อนหน้า ถือว่าอยู่ในยอดนั้นแล้ว จึงไม่หักอีก แก้หรือลบรายการเก่าก็ไม่ทำให้ยอดที่ปรับแล้วเพี้ยน

**ขึ้นรอบใหม่:** เมื่อถึงวันรับเงิน (วันที่เหลือ ≤ 0) ผู้ใช้ตั้งรอบใหม่ รอบเก่าเปลี่ยนเป็น closed แผนที่ยังเป็น "วางแผน" ย้ายตามไปรอบใหม่ (ผมตัดสินใจเอง)

## 7. ตัวตน (การ์ด 06)

**จากหน้าจอ LIFF**
1. หน้าจอเรียก `liff.getIDToken()` แล้วส่งมาใน header `Authorization: Bearer <id token>`
2. server ส่ง token ไปตรวจที่ LINE (`POST https://api.line.me/oauth2/v2.1/verify` พร้อม channel ID ของ LINE Login channel ที่มี LIFF app)
3. ผ่าน → ได้ `sub` (LINE user ID) → หาหรือสร้างแถวใน `users`
4. ทุกคำสั่งที่อ่านหรือเขียนข้อมูลใช้ `user_id` จากขั้นนี้เท่านั้น **ไม่เชื่อ user ID ที่ส่งมาใน body หรือ URL**
5. token หมดอายุหรือไม่ผ่าน → ตอบ 401 หน้าจอขอ token ใหม่

**LIFF หรือ MINI App (รวม main 12 พ.ย.):** หน้าจอของทีมเปิดเป็น MINI App (`2012545254`) ส่วน LIFF เดิมอยู่ใน LINE Login (`2012545176`) server รับ token ได้ทั้งสอง (`LINE_LOGIN_CHANNEL_ID` และ `LINE_MINIAPP_CHANNEL_ID`) โดยดู `aud` ใน token เพื่อเลือกว่าจะให้ LINE ตรวจกับ channel ไหน (LINE เป็นคนตรวจจริง ปลอมไม่ได้) · ทั้งสอง channel อยู่ Provider เดียวกัน คนเดียวจึงได้ผู้ใช้แถวเดียว (มีเทสต์) · ปุ่มเปิดแอปในแชตใช้ `appUrl()` → `miniapp.line.me/<id>` ถ้า `NEXT_PUBLIC_LIFF_ID` เป็นของ MINI App ไม่งั้น `liff.line.me/<id>`

**จากแชต (webhook)**
1. ตรวจ `x-line-signature` (HMAC-SHA256 ของ body ดิบด้วย channel secret) ไม่ตรง → ตอบ 401 และไม่ทำอะไร
2. ลายเซ็นตรง → เชื่อ `source.userId` ใน event ได้
3. บันทึก `webhookEventId` ลง `line_events` ก่อน ถ้าซ้ำ → ข้าม (LINE อาจส่ง event เดิมซ้ำ)
รวม main 12 พ.ย.: ตรวจลายเซ็นจาก byte ดิบ ไม่มี secret → 503 (จาก branch MINI App) · ข้อความ "พอใช้รุ่นทดสอบ Developing" ของ branch MINI App ถูกแทนด้วยบอทการ์ด 09/15 · คนแอดเพื่อน (follow) → ข้อความต้อนรับ + ปุ่มเปิดแอป
4. แชตแบบตัวต่อตัว (`source.type = "user"`) → หาหรือสร้างแถวใน `users` ด้วย `source.userId` **ฟังก์ชันเดียวกับ LIFF** (`userIdForLine`) · แชตกลุ่ม/ห้อง ไม่สร้างผู้ใช้

**บัญชีเดียวกันทั้งสองทาง ✅ (เกณฑ์การ์ด 06 ข้อ 1):** channel แชต (Messaging API) กับ channel LIFF (LINE Login) อยู่ใต้ Provider "PorChai" เดียวกัน LINE จึงให้ user ID ตัวเดียวกัน → ทักแชตก่อนหรือเปิด LIFF ก่อนก็ได้ผู้ใช้แถวเดียว (เทสต์ `lib/line/handle-event.db.test.ts`) · ถ้าวันหนึ่งย้าย channel ไปคนละ Provider จะได้ user ID คนละตัว และระบบจะแยกเป็นสองคน

## 8. API ที่หน้าจอเรียก (ชั้น 0–1)

ทุกเส้นต้องมี ID token ทุกคำตอบที่มีตัวเลขเงินมาจากตัวคำนวณเดียวกัน

| เส้น | ทำอะไร |
|---|---|
| `GET /api/me` | ข้อมูลผู้ใช้ + มีรอบ active หรือยัง |
| `POST /api/cycle` ✅ | ตั้งรอบใหม่ W4–W9 (แหล่งเงิน, ความถี่, วันรับเงิน, เงิน+เวลา, บิล ค้าง/จ่ายแล้ว/จ่ายแยก, ออม %/บาท, เผื่อ, ค่ากินค่ารถ, รายการเลื่อนได้) ใน transaction เดียว ผ่านฟังก์ชัน `create_cycle` (เรียกได้เฉพาะ service_role) · ออม+เผื่อห้ามเกินเงินที่มี · รอบเดิมยังไม่ถึงวันเงินเข้า → 409 `cycle_exists` · ถึงแล้ว → ปิดรอบเก่า ย้ายแผนที่ยังไม่จ่าย |
| `PUT /api/cycle/buffer` ✅ | การ์ด 19: ตั้งเงินเผื่อเป็นค่าใหม่ `{ amount, previous }` (ตั้งค่า ไม่ใช่ลบ → กดซ้ำไม่หักซ้ำ · `previous` ไม่ตรง → 409 `stale` · อัปเดตแบบมีเงื่อนไข สองหน้าจอพร้อมกันชนะได้หนึ่ง) · ออม+เผื่อ ≤ เงินที่มีตอนนี้ (`setAsideFits` ตัวเดียวกับตอนตั้งรอบและตอนลอง) · หน้าสรุปใช้ `POST /api/simulate { emergencyBuffer }` |
| `PUT /api/cycle/payday` ✅ | การ์ด 23: ยืนยันวันเงินเข้าใหม่ `{ payday, basis }` · `basis` ไม่ตรง → 409 `stale` · อัปเดตแบบมีเงื่อนไข · ไม่แตะรายจ่าย/ประวัติ ไม่เดาว่าเงินใหม่เข้า · ดูก่อนด้วย `POST /api/simulate { payday }` (นับแผนที่ครบกำหนดก่อนวันใหม่เข้ารอบนี้) · `plans` และ `cycle/balance` รับ `basis` ได้ด้วย |
| `POST /api/cycle/balance` ✅ | **ปรับยอด** (การ์ด 11): `{ balance, asOf? }` เก็บเป็นยอดอ้างอิงใหม่ใน `balance_checks` ไม่สร้างรายจ่าย · `asOf` เก่ากว่ายอดล่าสุด → 422 |
| `GET /api/summary` ✅ | เงินที่มี, เวลาของยอด, ใช้วันนี้, ออม, เผื่อ, ยอดกันไว้, ค่าจำเป็นต่อวัน + ผลตัวคำนวณ (งบต่อวัน, วันนี้เหลือ, ซื้อได้ไม่เกิน, ขาดค่าจำเป็น) · ยอดรวมตามหมวดยังไม่ทำ |
| `GET /api/entries` · `POST /api/entries` ✅ | ดูรายการที่ยังไม่ยกเลิกของรอบนี้ (ใหม่ก่อน) / เพิ่มรายจ่าย (ต้องมี header `Idempotency-Key` ไม่มี → 400 · key ซ้ำ → 200 รายการเดิม ไม่บันทึกเพิ่ม) |
| `PATCH /api/entries/:id` · `DELETE /api/entries/:id` ✅ | แก้ / **ยกเลิก** (ไม่ลบแถว ตั้ง `cancelled_at`) เฉพาะของเจ้าของ (ของคนอื่นหรือ id ผิดรูป → 404) · ยกเลิกซ้ำได้ผลเดิม · แก้รายการที่ยกเลิกแล้ว → 409 `entry_cancelled` · รายการที่เกิดจากจ่ายแผน → 409 `plan_entry` (ต้องย้อนที่แผน การ์ด 57) |
| `POST /api/simulate` ✅ | การ์ด 14 ลองก่อนจ่าย: ของที่จะซื้อ และ/หรือลองเลื่อนแผนที่กันอยู่ → ก่อน/หลัง + `verdict` (ok / essentials_short / shortfall / ask) + `needs` (essentials / payday) + เช็กบิล/ค่าจำเป็น/ออม/เผื่อ · **ไม่เขียนอะไรลงฐานข้อมูล** (เทสต์เทียบทุกแถวก่อน/หลัง) · ใช้ตัวโหลดเดียวกับ summary (`loadBudget`) |
| `PUT /api/cycle/essentials` ✅ | ตั้ง/แก้ค่ากิน + ค่ารถต่อวันของรอบนี้ (คำตอบของ `needs: ["essentials"]`) |
| `GET /api/plans` · `POST /api/plans` ✅ | ดูแผนของรอบนี้ / เก็บไว้ในแผน หรือเลื่อนไปรอบหน้า (W15) · ต้องมี `Idempotency-Key` |
| `POST /api/plans/:id/{pay,unpay,cancel,postpone,keep}` ✅ | การ์ด 57: ทุกปุ่มผ่านฟังก์ชัน `plan_action` (ล็อกแถวแผน transaction เดียว เรียกได้เฉพาะ service_role) · จ่ายแล้ว = สร้างรายจ่าย 1 รายการ + ปลดยอดกัน · กดซ้ำ/สองหน้าจอได้ผลเดิม · ทำไม่ได้จากสถานะปัจจุบัน → 409 `plan_status` · ของคนอื่น → 404 |
| `PUT /api/category-limits` | ตั้งวงเงินต่อหมวดของรอบนี้ |

รูปแบบ error: `{ "error": { "code": "...", "message": "ข้อความไทยสำหรับผู้ใช้" } }` · ข้อมูลไม่ผ่าน → 422 `invalid_input` · ยังไม่มีรอบเงิน → 409 `no_cycle`
รูปแบบ request/response อยู่ใน `lib/api-types.ts` (หน้าจอ import ได้) · **เงินเป็นสตางค์จำนวนเต็มทุกช่อง** (4500 = 45 บาท) · วันที่ `YYYY-MM-DD` เวลาไทย · คำตอบของ เพิ่ม/แก้/ยกเลิก/ปรับยอด แนบ `summary` ล่าสุดมาด้วย หน้าจอไม่ต้องเรียกซ้ำ

**ประวัติ (การ์ด 11):** ตาราง `history` บันทึกทุกการเพิ่ม/แก้/ยกเลิกรายจ่าย และทุกการเปลี่ยนสถานะแผน (ค้าง → จ่ายแล้ว/ยกเลิก) ด้วย trigger ในฐานข้อมูล เก็บค่าก่อน/หลังเป็น JSON · รายการที่ยกเลิกแล้วแก้หรือดึงกลับไม่ได้ (ฐานข้อมูลบังคับ)
**รายจ่ายจากการจ่ายแผน** (`source = 'plan'`) ไม่นับเป็น "ใช้วันนี้" เพราะเงินนั้นถูกกันไว้ในยอดกันแล้ว จ่ายบิลจึงไม่ทำให้งบวันนี้ติดลบ (Figma W15: จ่ายรองเท้า 480 → 80/วัน)

### จดผ่านแชต ✅ (การ์ด 09 · Figma L2, L6)

ทีมเปลี่ยนการ์ด 09 บนบอร์ดเป็น **"ข้อความชัด จดทันที"** (ไม่ต้องยืนยันก่อน) แบบเดิมที่มี `chat_drafts` จึงไม่ใช้แล้ว

1. ตัวอ่าน `lib/chat/parse.ts` (กฎล้วน ไม่มี AI): หายอดหนึ่งตัว + ชื่อ + หมวดจากคำ (ข้าว/กาแฟ → อาหาร · รถ/BTS/น้ำมัน → เดินทาง · ปากกา/ปริ้น/สบู่ → ของใช้ · อื่น ๆ) · รับ `บาท` `฿` `.-` ทศนิยม เลขไทย `1,200`
2. **ไม่ชัด → ถาม ไม่จด** พร้อมปุ่ม "กรอกเองในแอป": ไม่มียอด · หลายยอด · ยอดประมาณ ("ร้อยกว่า", "ประมาณ", "40-50") · ไม่มีชื่อ · ยอดเกิน 100,000 บาท · ไม่รองรับตัวเลขเป็นคำ ("ห้าสิบ")
3. **ชัด → จดทันที** (`source = chat`, `note` = ชื่อ, `idempotency_key = line:<webhookEventId>`) แล้ว reply "จดแล้ว ✓ ข้าว 45 บาท (อาหาร) · วันนี้ใช้ได้อีก 75 · ใช้ไปแล้ว 45 / 120"
4. **L6 เกินงบที่เหลือวันนี้ → พักไว้ ไม่จด** ถามพร้อมปุ่ม postback **[ยืนยันจ่ายจริง] [ลองก่อนซื้อ]** · ข้อมูลรายการอยู่ใน postback (ไม่ต้องมีตาราง draft) · ยืนยัน → จดด้วย key เดิมของข้อความแรก → กดซ้ำได้ "จดไว้แล้ว" ไม่จดเพิ่ม · ลองก่อนซื้อ → ตัวลองจ่ายการ์ด 14 ไม่บันทึกอะไร
5. **เกินงบวันนี้ไปแล้ว → รายการถัดไปจดทันที ไม่พักซ้ำ** (การพักมีไว้ตอนกำลังจะข้ามงบครั้งแรก) แต่คำตอบบอก "เกินงบวันนี้ X บาท" และ "พรุ่งนี้ใช้ได้ Y บาท/วัน (เดิม Z)" ทุกครั้ง เพราะส่วนที่เกินถูกเฉลี่ยออกจากวันที่เหลือ (ผู้ใช้ตกลง 12 พ.ย.)
6. ยังไม่ได้ตั้งรอบ → บอกให้ตั้งค่าในแอป
7. reply ใช้ reply token (ไม่กินโควตา) · reply ล้มเหลวไม่ทำให้รายการหาย
8. ปุ่มแก้/เปลี่ยนหมวด/ลบ ในข้อความตอบกลับ (L2) = การ์ด 10 ของโฟรวิว ต่อจาก `recordedMessage` ใน `lib/chat/messages.ts`

### แชตคุยกับ AI ✅ (การ์ด 15 "AI เข้าใจคำถาม" · ทำเกินการ์ด ผู้ใช้ตกลง 12 พ.ย.)

**กฎอ่านก่อนเสมอ AI ใช้เฉพาะตอนกฎอ่านไม่ออก** (`lib/line/handle-event.ts` → `onText`, AI ใน `lib/chat/converse.ts`):

| ข้อความ | ใครอ่าน | ผล |
|---|---|---|
| «ข้าว 45» | กฎ | จดทันที (เหมือนเดิม ไม่เรียก AI ประหยัดโควตา) |
| «ชาบู 300 ไหวไหม» «ถ้ากินชาบู 150 จะเหลือวันละเท่าไร» (คำถาม/คำสมมติ มีราคาเดียว) | การ์ด 15 เดิม | คำแนะนำ + ปุ่ม · **ไม่จดเด็ดขาด** |
| คำถามไม่มีราคา แต่มีชื่อร้านในตาราง `price_hints` «ถ้ากินตี๋น้อยจะเหลือเท่าไร» | กฎ (`findPriceHint`) | "สุกี้ตี๋น้อย ราคาประมาณ 279 บาท/คน (ทีมเช็คเมื่อ …)" + ปุ่ม [ใช้ราคานี้ลอง] [พิมพ์ราคาเอง] หรือพิมพ์ «250» → การ์ดลองก่อนจ่าย · **ไม่จดเด็ดขาด** · ไม่เรียก AI |
| คำถามไม่มีราคาหรือหลายราคา «ชาบู 150 หรือ 200 ดี» | AI คุย | ไม่แยกยอด ไม่ถาม "จ่ายไปกี่บาท" (ถาม "ราคาเท่าไร" แทน คำตอบไม่ถูกจด) |
| «45» | กฎ | "45 บาท ค่าอะไร?" แล้วจำยอด → ตอบ «ข้าว» = จด |
| «ข้าว 45 น้ำ 20» | AI แยก | เสนอรายการ + รวม (+ บอกถ้าเกินงบวันนี้) ปุ่ม **[จดทั้งหมด] [ไม่ใช่]** · กดแล้วจดเลยแม้เกินงบ (ผู้ใช้ตกลง) · AI ล่ม/แยกผิด → "ส่งทีละรายการ" |
| «ข้าว» / «ข้าวร้อยกว่า» | AI | "ข้าว จ่ายไปกี่บาท?" แล้วจำชื่อ → ตอบ «45» = จด (ผ่านการพัก L6 เหมือน «ข้าว 45») |
| «เหลือเท่าไร» «เหลือกี่บาท?» «เหลือเงินทั้งหมดเท่าไร» «งบเหลือป่ะ» «วันนี้ใช้ไปเท่าไร» «เช็คยอด» (ทั้งข้อความมีแต่คำถามยอด ไม่มีชื่อของ/ตัวเลข/ช่วงเวลาอื่น) | กฎ (`isBalanceQuestion`) | การ์ดงบวันนี้ของโฟรวิว + บรรทัด "เงินทั้งหมดตอนนี้" · ไม่เรียก AI ตัวเลขจากโค้ดเสมอ · «สัปดาห์นี้/เดือนนี้ใช้ไปเท่าไร» ยังไป AI (ตกลง 13 พ.ย.) |
| «Hey» «ชาบูไหวไหม» | AI | คุยกัน เฉพาะเรื่องเงิน/การใช้แอป |

**โมเดล:** `gemini-3.1-flash-lite` (ค่าเริ่มต้น เปลี่ยนได้ด้วย `GEMINI_MODEL`) · รอสูงสุด 15 วิ รวมลองใหม่ 1 ครั้งเมื่อ Google ตอบ 503 · เลือกจาก `npm run eval:chat` 13 พ.ย. (54 ข้อความ): 3.1-flash-lite ตอบได้ 36 · 3.5-flash-lite 18 (503 "high demand" บ่อย) · 2.5-flash-lite ปิดสำหรับ key ใหม่ · AI ห้ามบอกขั้นตอนหน้าจอ (มันไม่เห็นหน้าจอ เคยแต่ง "กดค้างที่รายการ") ให้ชี้ปุ่มเปิดแอปแทน · log `chat-ai outcome=… ms=…` ไม่มีข้อความผู้ใช้

**บั๊ก 13 พ.ย. (แก้แล้ว):** «ถ้ากิน ชาบู 150 บาท จะเหลือเงินใช้วันละเท่าไร» ถูกจดเป็นรายจ่าย 150 เพราะตัวจับคำถามรู้จักแค่ ไหวไหม/ได้ไหม/? · ตอนนี้จับ ถ้า สมมติ หาก ควร เท่าไร กี่ ยังไง ทำไม หรือเปล่า ป่ะ ไหม(ท้าย) + คำลงท้าย ครับ/นะ · คำที่อยู่ในชื่อของได้ (น้ำเปล่า ผ้าไหม มะม่วง) จับเฉพาะตำแหน่งที่เป็นคำถามได้ · ตารางทดสอบ 24 คำถาม + 20 รายจ่ายใน `lib/advice/question.test.ts` · คำถามทุกแบบไม่ผ่านเส้นทางที่จด

**ตารางราคาประมาณ `price_hints` (13 พ.ย.):** ทีมขอให้หาราคาเองเมื่อไม่บอกราคา → เลือกตารางที่ทีมดูแลแทน web search (ราคาจากเว็บเชื่อไม่ได้ + Gemini ฟรีล้นอยู่แล้ว · web search จริงอยู่ในสไลด์ "แผนต่อไป") · ใส่ 6 ร้านใน migration `20261113300000` พร้อมลิงก์แหล่ง: ตี๋น้อย 279 · ชาบูชิ 319 · บาร์บีคิวพลาซ่า 399 · Sukishi 520 · Amazon ลาเต้เย็น 75 · Starbucks ลาเต้ Tall 130 (ชาบูชิ/Sukishi คำนวณรวมน้ำ+ภาษีเอง · BBQ แคมเปญจบ 27 ก.ย. — เช็คก่อนเดโม)
- **ทีมแก้ราคาเอง:** Supabase Studio → Table Editor → `price_hints` · แก้ `price` เป็น**สตางค์** (279 บาท = 27900) แล้วแก้ `checked_on` เป็นวันที่เช็ค · เพิ่มชื่อที่คนพิมพ์ใน `aliases` (เว้นวรรค/ตัวพิมพ์ไม่มีผล) · ปิดร้านด้วย `active = false` (ไม่ต้องลบ) · ไม่ต้อง deploy
- จับเฉพาะ**คำถาม**ที่ไม่มีราคา · «กินตี๋น้อย» (ไม่ใช่คำถาม อาจเป็นการจด) ไปทางเดิม · ชื่อยาวสุดชนะ (ชาบูชิ ไม่ใช่ ชาบู)
- ปุ่ม `try_hint` (postback ใหม่) · และ `onTryButton` จ่ายจริงได้เฉพาะ `pay_real` แล้ว — เดิมปุ่มที่ส่งมาแต่ไม่ได้ต่อสาย **ตกไปจ่ายจริง** (เจอจากการลองทำพัง)
- ⚠️ รู้แล้วยังไม่แก้: «ถ้ากินตี๋น้อย 2 คนจะเหลือเท่าไร» อ่านเลข 2 เป็นราคา 2 บาท (ปัญหาเดิมของ `readQuestion`)

**ตัวกัน (โค้ดตัดสิน ไม่ใช่ AI):**
- ตัวเลขในคำตอบต้องอยู่ใน facts (`todayRemaining`, `dailyBudget`, `spentToday`, `balance`, `reserved`, `daysLeft` หน่วยบาท) หรือที่ผู้ใช้พิมพ์ในแชต 30 นาที · ห้ามแนะนำลดค่ากินค่ารถ/ใช้เงินออม · ห้ามบอกว่า "จดแล้ว/บันทึกแล้ว" (มีแต่โค้ดที่จด) · ยาวไม่เกิน 400 ตัวอักษร
- **นอกเรื่อง:** AI ต้องติดป้าย `topic` (money/app/greeting/other) ถ้า `other` → ทิ้งคำของ AI ทั้งหมด ตอบแม่แบบ "เรื่องนี้พอใช้ช่วยไม่ได้นะ ถามเรื่องเงินได้เลย" · ไม่มีป้าย/ป้ายแปลก = อ่านไม่ได้ → แม่แบบ · ⚠️ ถ้า AI ติดป้ายผิดเป็น money แต่ตอบนอกเรื่อง ตัวกันนี้จับไม่ได้ เหลือตัวกันตัวเลข/ความยาวช่วย
- รายการที่ AI แยก: ชื่อต้องอยู่ในข้อความที่พิมพ์ · ยอดต้องเป็นตัวเลขที่พิมพ์ (พิมพ์ซ้ำกี่ครั้งใช้ได้เท่านั้น) · หมวดใช้กฎ ไม่ใช้ AI · สูงสุด 5 รายการ
- AI เสนอ ผู้ใช้กดยืนยันเสมอ · กด [จดทั้งหมด] ซ้ำ = จดครั้งเดียว (key `line:<eventId>:<ลำดับ>`) · ปุ่มเก่าเกิน 30 นาที → "หมดเวลาแล้ว"
- AI ล่ม/ไม่มีคีย์/โควตาหมด/ไม่ผ่านตัวกัน → แม่แบบ: "สวัสดีครับ ผมชื่อพอใช้ ผู้ช่วยเรื่องเงินของคุณ" + วันนี้ใช้ได้อีก X (ยังไม่ตั้งรอบ → ชวนตั้งรอบ) · ตัดรายการ "ช่วยได้ 3 อย่าง" ออกตามที่ผู้ใช้สั่ง 13 พ.ย.

**ส่งให้ Google (Gemini):** ข้อความล่าสุด + แชตทั้งสองฝั่งใน 30 นาที (สูงสุด 10 บรรทัด) + facts ตัวเลข · ไม่ส่ง LINE ID ชื่อ หรือรายการจากฐานข้อมูล (มีเทสต์) · ⚠️ ต้องบอกในหน้ายินยอม W1–W3

**"จดแล้ว ✓" แบบกันเอง (ไม่ใช้ AI ไม่มีตัวเลข):** บรรทัดท้ายตามงบที่เหลือ — เหลือ ≥ ครึ่ง "ยังเหลืออีกเยอะ ใช้ได้สบาย ๆ ครับ" · น้อยกว่าครึ่ง "เหลือไม่มากแล้ว ค่อย ๆ ใช้นะครับ" · เหลือ 0 "พอดีงบวันนี้เป๊ะเลยครับ" · เกินงบ "ไม่เป็นไรครับ งบพรุ่งนี้ปรับให้แล้ว" · **น้ำเสียงบอท: ผู้ชาย ลงท้าย "ครับ"** (ผู้ใช้เลือก 13 พ.ย.) ทั้ง prompt ของ AI และแม่แบบที่เพิ่มในงานนี้ · แม่แบบเดิมตาม Figma (L2/L6/advice) ยังไม่เปลี่ยน

### การ์ด "จดแล้ว" แบบ Flex ✅ (การ์ด 10 · หน้าตาการ์ดของโฟรวิว `lib/line/flex` · ต่อสายฝั่งพอ 13 พ.ย.)

- จด 1 รายการ («ข้าว 45», ตอบยอดหลัง «ข้าว», ยืนยันจ่ายจริง, จ่ายแผน) → `buildRecordedCard` ผ่าน `lib/chat/cards.ts` · บรรทัดกันเองอยู่ใน `subnote` ของการ์ด · งบไม่ปกติ (ขาด/ถึงวันเงินเข้า) ใช้ข้อความเดิม
- จดหลายรายการ [จดทั้งหมด] ยังเป็นข้อความ เพราะปุ่ม [แก้][ลบ] บนการ์ดผูกได้รายการเดียว
- ปุ่ม (รูปแบบ `v1.<action>.<id>` ตาม `lib/line/flex/postback.ts`): **เปลี่ยนหมวด** → ปุ่มด่วน 4 หมวด (`entry_cat_set.<id>.<หมวด>`, Figma L9) · **ลบ** → ถาม [ลบเลย] (`entry_del_ok`) ไม่มี "เลิกทำ" เพราะ DB ห้ามยกเลิกการลบ · **แก้** → "พิมพ์ยอดใหม่" แล้วข้อความถัดไป «50» แก้ยอด (pending `edit` ในความจำแชต) + ลิงก์แก้ในแอป `/app/record/<id>` · **วันนี้ใช้ได้** → `buildTodayBudgetCard`
- id ทุกตัวเช็คเจ้าของ (`entryForChat` → 404 ถ้าไม่ใช่ของคนนั้น มีเทสต์ปุ่มปลอม) · ปุ่มของการ์ดอื่นที่ยังไม่ต่อสาย → "ปุ่มนี้ยังใช้ไม่ได้ครับ" (การ์ดเตือน `rem_*` = การ์ด 58 ถัดไป)

**ข้อความหายเมื่อจัดการไม่สำเร็จ (แก้แล้ว):** ถ้าจดไม่สำเร็จ webhook ลบ `webhookEventId` ออกจาก `line_events` แล้วตอบ 500 ให้ LINE ส่งซ้ำ จดซ้ำไม่ได้เพราะ key ผูกกับ event · ⚠️ ต้องเปิด **Webhook redelivery** ใน LINE Developers ด้วย

**ปุ่ม [เปิดแอป] ทุกคำตอบ (13 พ.ย.):** `withAppButton` ใน `lib/line/reply.ts` เติมปุ่มด่วน "เปิดแอป" ให้ทุกข้อความที่ยังไม่มี ตรงจุดที่ส่งออก (ตอบแชต + push เตือน) · ปุ่มด่วนของ LINE หายเมื่อมีข้อความใหม่ ช่องที่อยู่ตลอดคือ rich menu

### การ์ดลองก่อนซื้อ / เทียบ AI / ต้อนรับ ✅ (การ์ดของโฟรวิว · ต่อสาย 13 พ.ย. · ผู้ใช้อยากให้คุยเป็น flex ส่วนใหญ่)

### เตือนรายการประจำ ✅ (การ์ด 58 · การ์ดเตือนของโฟรวิว · 13 พ.ย.)

**ตัดสินกับผู้ใช้ 13 พ.ย.:** เตือนวันละครั้งตามเวลาที่ผู้ใช้ตั้ง (ค่าเริ่มต้น 12:30 ปิดไว้จนผู้ใช้เปิด) · รายการประจำ = ชื่อเดียวกัน ≥ 3 วันใน 7 วันล่าสุด (Figma F2) · ตัวตั้งเวลา Supabase Cron ทุก 15 นาที · เดโมพิมพ์ «เดโมเตือน» (เฉพาะ `DEMO_MODE=1`)

- **กฎ** (`lib/remind/habits.ts` ฟังก์ชันล้วน): นับรายการที่จดแล้ว ไม่นับที่ลบ/จ่ายแผน/บิล · ยอดปกติ = ค่ากลาง (median ตัวล่าง) · เวลาปกติ = ค่ากลางของเวลาที่จด (เวลาไทย) · หมวด = ล่าสุด · เตือนเมื่อ ถึงเวลาที่ตั้ง + รายการนั้นปกติจดก่อนเวลานั้น (ข้าวเย็นไม่ถูกเตือนตอน 12:30) + วันนี้ยังไม่จดชื่อนั้น + วันนี้ยังไม่เคยเตือน/จด/ข้าม · รายการมากสุดก่อน วันละ 1 ข้อความ
- **ตาราง:** `reminder_settings` (enabled, remind_at, paused_until) · `reminder_log` (habit_key, label, amount, category, day, status sent/recorded/skipped, entry_id) unique (user, habit, day) = กันเตือนซ้ำแม้ cron สองรอบชนกัน · ทั้งคู่ revoke anon + RLS
- **ตัวตั้งเวลา:** `pg_cron` job `porchai-reminders` ทุก 15 นาที เรียก `run_reminders()` → ลบแชตเกิน 30 นาที (ปิดช่องที่ trigger รอคนพิมพ์) แล้ว `pg_net` POST `/api/cron/reminders` พร้อม `Authorization: Bearer <cron_secret>` · URL และรหัสอยู่ใน Supabase Vault (`cron_secret`, `reminders_url`) ตั้งเฉพาะบน cloud ฐานข้อมูลในเครื่อง/เทสต์จึงไม่เรียกอะไร · Vercel ต้องมี `CRON_SECRET` ค่าเดียวกัน (ไม่มี → 503)
- **ส่ง:** LINE push (`lib/line/push.ts`, `X-Line-Retry-Key` = id ของ log) การ์ด `buildHabitReminderCard` · push ล้ม → ลบแถว log ให้รอบหน้าส่งใหม่ · ⚠️ push กินโควตา OA รายเดือน
- **ปุ่ม** (`v1.rem_*.<logId>` เช็คเจ้าของ): ใช่ จดเลย → จดยอดปกติ `source=reminder` key `reminder:<logId>` → การ์ดจดแล้ว · แก้ยอด → ถามยอด (pending `reminder`) «60» จดด้วย key เดียวกัน (กดใช่ซ้ำ/แก้แล้วกดใช่ = จดครั้งเดียว) · วันนี้ไม่ได้ซื้อ → status skipped ไม่เตือนซ้ำวันนี้ · ยกเลิกการแก้ → ไม่จด · จดลงวันที่ของการเตือน (`day`)
- **API หน้าจอ:** `GET/PUT /api/reminders` ตามรูปแบบ `ReminderSettings` ของโฟรวิว (ต่อสายใน `lib/client/live.ts` แล้ว)
- **เดโม (`DEMO_MODE=1`):** «เดโมเตรียม» ใส่ ข้าวเที่ยง 50 เวลา 12:10 ย้อนหลัง 3 วันให้บัญชีของคนพิมพ์ (key ตามวัน พิมพ์ซ้ำไม่เพิ่ม · เป็นรายจ่ายจริงในรอบ ผู้ใช้ตกลง) · «เดโมเตือน» ส่งการ์ดเตือนทันทีเป็น reply (ไม่กินโควตา)

## 10. ชั้น 3–7 (กรอบไว้ ยังไม่ละเอียด)

- **AI แนะนำก่อนจ่าย ✅ (การ์ด 15):** `POST /api/advice { question }` และคำถามในแชต (มีคำว่า ไหวไหม / พอไหม / ได้ไหม / ?) → AI อ่านคำถาม (ยอดต้องตรงกับตัวเลขที่พิมพ์ วันมาจากคำ วันนี้/พรุ่งนี้/มะรืน ไม่ตรง → ถาม) → ตัวลองจ่าย (การ์ด 14) คำนวณ + ทางเลือก ลดงบ (ซื้อได้ไม่เกิน) / เลื่อนแผนที่กันไว้ / ใช้เงินเผื่อ (เฉพาะเมื่อผู้ใช้อนุญาต) · ไม่เคยแนะนำลดค่ากินค่ารถ → AI เขียนคำอธิบายจาก JSON ตัวเลข · **ใช้คำของ AI เฉพาะเมื่อทุกตัวเลขมาจากตัวคำนวณ** ไม่มีคำต้องห้าม และบอกยอดขาดเมื่อขาด ไม่งั้นใช้ข้อความแม่แบบ (`byAI: false`) · AI ล่ม/ไม่มีคีย์/โควตาหมด → กฎ + แม่แบบ · verdict: enough=เงินพอ, tight=เงินตึง (จ่ายได้แต่งบต่อวันต่ำกว่าค่ากินค่ารถ), short=เงินไม่พอ, ask=ข้อมูลไม่ครบ (ผู้ใช้ตกลง 12 พ.ย.) · ไม่บันทึกอะไร ยืนยันด้วยปุ่ม ยืนยันจ่ายจริง / เก็บไว้ในแผน (เก็บแล้วกดจ่าย = จ่ายแผนนั้น · จ่ายแล้วกดเก็บ = ไม่กันซ้ำ) · Gemini Interactions API รุ่น `gemini-3.5-flash-lite` `store: false` (`lib/ai/gemini.ts`) ⚠️ รูปแบบคำตอบของ REST ยังไม่ได้ยืนยันกับคีย์จริง ถ้าอ่านไม่ได้จะตกไปใช้แม่แบบ
- **AI (ชั้น 3):** AI แปลงข้อความเป็นข้อมูลมีโครงสร้าง (structured output) → ตัวคำนวณคำนวณ → ส่งผลตัวเลขให้ AI อธิบายเป็นภาษาคน AI ห้ามสร้างตัวเลขเงินเอง ตัวเลขในคำตอบต้องมาจากผลคำนวณที่ส่งให้ ส่งข้อมูลเฉพาะที่จำเป็น ไม่ส่งชื่อหรือ LINE ID
- **OCR สลิป ✅ (ชั้น 4 · 13 พ.ย. · การ์ดร่างของโฟรวิว `buildOcrDraftCard`):** ส่งรูปในแชต → `lib/line/content.ts` ดึงรูปจาก LINE (ไม่เก็บรูป) → `readSlip` (`lib/ocr/slip.ts`) Gemini `generateContent` + inline_data → `slipFrom` กัน: ยอด >0 ≤100,000 บาท · วันที่จริง ไม่เกินวันนี้ ไม่เก่ากว่า 30 วัน · prompt ห้ามส่งเลขบัญชี/เลขอ้างอิง → การ์ดร่าง **ไม่จดจนกด [บันทึก]** · ร่างอยู่ในความจำแชต 30 นาที (pending `ocr` อ่านฉบับล่าสุด ยกเลิก/โอน = closed) · ปุ่ม `v1.ocr_*`: บันทึก (รายจ่าย source `ocr` / รายรับ) key `ocr:<draftId>` ครั้งเดียว · แก้ยอด · เลือกยอด (ต้องเป็นยอดที่อ่านได้) · ไม่แน่ใจประเภท/โอน → ถาม (โอน = ไม่จด) · ยอดเท่ากันวันเดียวกัน → เตือนว่าอาจซ้ำ · อ่านไม่ออก/Gemini ล้น → ให้พิมพ์เอง · **ความเป็นส่วนตัว:** รูปส่งให้ Gemini แผนฟรี (ผู้ใช้ตกลง) ต้องบอกในหน้ายินยอม · ยืนยันกับ Gemini จริงด้วยสลิปปลอม (`scripts/slip.eval.ts` 1.5 วิ อ่านถูก)
- **โปร (ชั้น 5):** รหัสสุ่ม unique ต่อการกดรับ หน้าร้านยืนยันด้วย PIN ร้าน การยืนยันซ้ำได้ผลเดิม
- **แต้ม (ชั้น 6):** เช็กครบแล้ว 1 แต้มต่อวันไทย (unique) แลกของหักแต้มและสต็อกใน transaction เดียว
- **รายงานร้าน (ชั้น 7):** แสดงเฉพาะกลุ่มที่มีอย่างน้อย 5 คน กันการระบุตัวบุคคล

- ยังไม่ทำ "รายการที่ลดหรือเลื่อนได้" (W8) แบบเต็ม — ตอนนี้ใช้แผน `purchase` ที่มี `due_on` แทน ช่องลดได้เหลือเท่าไร/เลื่อนได้ไหม ทำพร้อมการ์ด 23
- รายงานร้านขั้นต่ำ 5 คน
- แผน (การ์ด 57, ผู้ใช้เลือก 12 พ.ย.): หมวดของรายจ่ายที่จ่ายจากแผน ส่งได้ตอนเก็บหรือตอนจ่าย ไม่ส่ง = อื่น ๆ และเปลี่ยนหมวดทีหลังได้ (ยอดแก้ไม่ได้) · "เลื่อนไปรอบหน้า" เป็นสถานะ `postponed` · มี "ยกเลิกการจ่าย" (เกินเกณฑ์การ์ด)
- แผนที่เลื่อนไว้ ตั้งรอบใหม่แล้วกลับมาเป็น "วางแผน" ทันที (กันเงินไว้ก่อน ไม่ให้เห็นเงินมากกว่าที่มี) — ผมตัดสินใจเอง
- ลองก่อนจ่าย (การ์ด 14): ของที่ลองนับเป็นยอดกันทั้งก้อน (แบบ Figma W12 480 → 80/วัน) · ชื่อ `verdict` ตามคำใน Figma ไม่ใช้ "พอ/ตึง" เพราะยังไม่มีนิยาม "ตึง" (การ์ด 15 ค่อยแปลงเป็นคำพูด) · ค่ากินค่ารถที่ตอบตอนลอง ใช้แค่ครั้งนั้น ถ้าจะจำต้องเรียก `PUT /api/cycle/essentials` (ผู้ใช้เลือกให้ทำทั้งสองทาง 12 พ.ย.)
- เงินเผื่อ (การ์ด 19): ไม่มีหน้ายืนยันใน Figma (มีแค่ "ปรับ ›") จึงใช้ ลอง → ยืนยัน แบบเดียวกับลองก่อนจ่าย · เพดานใช้กติกาเดียวกับตอนตั้งรอบ (ออม+เผื่อ ≤ เงินที่มี) ไม่ใช่ "เงินใช้ได้ต้องไม่ติดลบ" — ตั้งเงินเผื่อจนเงินใช้ได้ติดลบได้ ระบบจะแสดง shortfall ตามจริง
- แผนเก่า (การ์ด 23 + ข้อ version ของการ์ด 05): ใช้ `basis` = แฮชของตัวเลขทั้งหมดที่ตัวคำนวณใช้ (`basisOf` ใน `lib/db/budget.ts`) แทนคอลัมน์ `version` เพราะจับการเปลี่ยนได้ทุกแหล่ง (รายจ่าย แผน ปรับยอด ค่าตั้ง ข้ามวัน) โดยไม่ต้องมี trigger · คอลัมน์ `cycles.version` / `plans.version` ไม่ได้ใช้เช็กนี้ (`plans.version` ใช้ทำ key ของรายจ่ายจากแผน)
