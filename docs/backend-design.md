# เอกสารออกแบบ Backend — พอใช้

ร่าง 11 พ.ย. 2569 · ผู้เขียน: พอ (Backend) · สถานะ: อนุมัติ 11 พ.ย. · แก้ 11 พ.ย.: ใช้ LIFF แทน MINI App ตาม tech stack ที่ทีมกำหนด · แก้ 11 พ.ย. ค่ำ: สูตรและตารางตาม Figma "Slides (สำหรับเพื่อน)" (เงินออม, ค่าจำเป็นต่อวัน, ซื้อได้ไม่เกิน, ปรับยอด, บิลจ่ายแยก, 4 หมวด)

**Tech stack (ทีมกำหนด):** LINE OA + Messaging API · LIFF · Next.js + TypeScript · Supabase PostgreSQL · AI API (ยังไม่เลือกเจ้า) · Vercel · Microsoft Clarity · ทดสอบด้วย Vitest (เครื่องมือตอนพัฒนา ไม่อยู่ในแอป)
ยึดขอบเขตจาก "สรุป Final สำหรับทีม 11 พ.ย." ครอบคลุมการ์ด 03 (สูตร), 05 (ข้อมูล), 06 (ตัวตน) และวางทางให้ชั้นถัดไป

---

## 1. เจตนา

นักศึกษาต้องเห็น **ตัวเลขเดียวที่เชื่อได้**: วันนี้ใช้ได้อีกเท่าไรโดยยังพอถึงวันรับเงิน ตัวเลขนี้ต้องตรงกันทุกทาง (แชต, หน้าจอ LIFF, การเตือน, AI) และห้ามผิดหรือหักซ้ำ เพราะถ้าผู้ใช้เจอยอดผิดครั้งเดียวก็เลิกเชื่อแอป

Backend จึงมีหน้าที่หลักสองอย่าง
1. **ตัวคำนวณเดียว** ที่ทุกทางเรียกใช้
2. **การบันทึกที่เกิดครั้งเดียวและเป็นของเจ้าของบัญชีเท่านั้น** (R01, R02)

## 2. เป้าหมาย / ไม่ทำ / ห้ามเกิด

**เป้าหมาย** (เรียงตามชั้น ทำชั้นล่างให้ผ่านเทสต์ก่อนขึ้นชั้นบน)

| ชั้น | สิ่งที่ใช้งานได้ |
|---|---|
| 0 | ตรวจตัวตน, ตารางข้อมูล, ตัวคำนวณพร้อมเทสต์ |
| 1 | จดผ่านแชตและฟอร์ม → ยืนยัน → บันทึกครั้งเดียว · ตั้งรอบเงิน · สรุป · แก้/ลบรายการ · ลองก่อนจ่าย · วางแผน/จ่ายแล้ว |
| 2 | เตือนจากพฤติกรรม |
| 3 | AI อ่านข้อความแชตและช่วยคิดก่อนจ่าย |
| 4 | OCR ใบเสร็จ |
| 5 | โปรร้าน + รหัสใช้สิทธิ์ |
| 6 | แต้มรายวัน + แลกของ |
| 7 | รายงานรวมให้ร้าน (ถ้าไม่ทัน ใช้ตัวเลขจำลองในสไลด์) |

**จุดตรวจ:** 13–14 พ.ย. ตรวจระบบรวม ไม่เลื่อน ถ้าชั้นไหนไม่เสร็จให้ตัดชั้นนั้นและชั้นที่สูงกว่า

**ไม่ทำรอบนี้:** เชื่อมธนาคาร, โอน/ล็อกเงินจริง, จดกลุ่ม, ระบบบัญชีร้านเต็มรูปแบบ, ต่ออายุสมาชิก

**ห้ามเกิด (แม้ระบบจะ "ทำงานได้")**
- AI หรือระบบบันทึกรายจ่ายเองโดยผู้ใช้ไม่ได้กดยืนยัน
- ตัวเลขเงินมาจาก AI แทนที่จะมาจากตัวคำนวณ
- ผู้ใช้ A เห็นหรือแก้ข้อมูลของ B ได้ แม้แก้รหัสในคำขอ
- ยอดติดลบแต่หน้าจอแสดงงบที่ดูเหมือนยังมีเงิน
- key หรือข้อมูลจริงหลุดขึ้น repo (repo เป็น public)

## 3. ข้อจำกัด

- เวลา: เหลือ 7 วัน คนเขียน back คนเดียว
- งบโครงการรวม 960 บาท
- **LINE OA แผนฟรี:** push ใช้โควตา (แหล่งรองรายงาน 300 ข้อความ/เดือนสำหรับไทย ยังไม่ยืนยันจากหน้า LINE ทางการ) ส่วน reply ไม่กินโควตา → ตอบในแชตด้วย reply เสมอ ใช้ push เฉพาะการเตือน
- **Vercel Hobby:** cron รันได้วันละครั้ง และเวลาคลาดได้ทั้งชั่วโมง → ใช้ตั้งเวลาเตือน 12:30 ไม่ได้ (ดูข้อ 9)
- **LIFF:** สร้าง LIFF app ใน LINE Login channel ที่อยู่ Provider เดียวกับ Messaging API channel (LINE user ID แยกตาม Provider) การเตือนส่งผ่าน OA ไม่ใช้ service message
- **Microsoft Clarity (ฝั่งหน้าจอ):** ต้องปิดบังยอดเงิน ชื่อรายการ และรายละเอียดรายจ่ายทุกจุด (NFR04) ก่อนเปิดให้ผู้ทดลองใช้
- วันที่และ "วันนี้" ใช้เวลาไทย `Asia/Bangkok` เสมอ

## 4. ภาพรวมระบบ

```
นักศึกษา ─┬─ แชต LINE OA ──► webhook (/api/line/webhook) ─┐
          └─ หน้าจอ LIFF (Next.js) ──────► /api/* ───────┤
                                                          ├─► บริการกลาง (lib/) ─► Supabase Postgres
ตัวตั้งเวลา (Supabase cron) ──► /api/cron/reminders ───────┘        │
                                                                    └─► LINE Messaging API (reply / push)
```

- โค้ดทั้งหมดอยู่ใน repo เดียว deploy บน Vercel
- หน้าจอเรียกข้อมูลผ่าน `/api/*` เท่านั้น ไม่ต่อฐานข้อมูลตรง
- ฐานข้อมูลเปิด RLS ทุกตารางและไม่มี policy ให้ anon เลย → มีแค่ server (service role key) ที่อ่านเขียนได้ การกรองตามเจ้าของบัญชีทำในโค้ด back ทุกคำสั่ง

## 5. หลักเงินและสูตร (การ์ด 03)

### คำศัพท์

| คำ | ความหมาย |
|---|---|
| เงินตั้งต้นของรอบ | ยอดเงินที่ผู้ใช้มีตอนตั้งรอบ พร้อมเวลาที่ยอดนั้นจริง (W5 "แก้เวลา") |
| ยอดอ้างอิง | ยอดที่ผู้ใช้บอกล่าสุด: เงินตั้งต้น หรือยอดจาก "ปรับยอด" ครั้งล่าสุด (ตาราง `balance_checks`) |
| เงินจริงตอนนี้ | ยอดอ้างอิง − รายจ่ายที่จด **หลัง** เวลาของยอดอ้างอิง และเป็นของวันนั้นหรือหลังจากนั้น (`balanceNow`) |
| เงินออม | หักตั้งแต่ต้นรอบ เลือกเป็น % ของเงินตั้งต้น (ปัดลงเป็นบาท) หรือกรอกเป็นบาท ไม่นับในงบใช้จ่าย |
| เงินเผื่อ (ฉุกเฉิน) | ยอดที่ผู้ใช้กันไว้ ไม่นำมาหารเป็นงบรายวัน |
| ยอดกันไว้ | บิลค้าง + แผนที่สถานะ "วางแผน" ที่ครบกำหนดไม่เกินวันรับเงิน (`reservedTotal`) · บิลจ่ายแล้ว/จ่ายแยก/ยกเลิก ไม่นับ · ครบกำหนดหลังวันรับเงิน = รอบหน้า (W8) |
| เงินใช้ได้ | เงินจริงตอนนี้ − เงินเผื่อ − เงินออม − ยอดกันไว้ |
| ค่าจำเป็นต่อวัน | ค่ากิน + ค่าเดินทางต่อวันที่ผู้ใช้ตั้ง (W7) |
| วันที่เหลือ | จำนวนวันจากวันนี้ (นับวันนี้) ถึงวันก่อนวันรับเงิน |

### สูตร

```
งบต่อวัน        = เงินใช้ได้ ณ ต้นวันนี้ ÷ วันที่เหลือ
วันนี้เหลือ      = งบต่อวัน − รายจ่ายวันนี้
ซื้อได้ไม่เกิน    = เงินใช้ได้ ณ ต้นวันนี้ − ค่าจำเป็นต่อวัน × วันที่เหลือ   (ไม่ต่ำกว่า 0)
ขาดค่าจำเป็นวันละ = ค่าจำเป็นต่อวัน − งบต่อวัน                         (ไม่ต่ำกว่า 0)
พรุ่งนี้ใช้ได้     = สูตรเดียวกัน โดยวันนี้ = พรุ่งนี้ และรายจ่ายวันนี้ = 0
```

"ณ ต้นวันนี้" หมายถึงไม่นับรายจ่ายของวันนี้ (คือเงินใช้ได้ตอนนี้ + รายจ่ายที่ `spent_on` = วันนี้) งบต่อวันจึงคงที่ตลอดวัน ผู้ใช้เห็นยอดลดลงตามที่จ่าย ไม่ใช่งบที่แกว่งทุกครั้งที่จด ส่วนแผน "วางแผน" ที่สร้างระหว่างวันมีผลทันที เพราะผู้ใช้ตั้งใจกันเงินนั้นแล้ว

"ซื้อได้ไม่เกิน" ใช้ฐานต้นวันเหมือนงบต่อวัน จึงคงที่ทั้งวัน (Figma W12: จดข้าว 45 แล้วยังเป็น 600) ตรงกับการลองจ่ายที่คิดจากฐานเดียวกัน

**ปรับยอด (กันหักซ้ำ R01):** ไม่เก็บยอดคงเหลือแบบวิ่ง แต่เก็บ "ยอดที่ผู้ใช้บอก + เวลาที่ยอดนั้นจริง" รายจ่ายที่จดก่อนเวลานั้น หรือเป็นของวันก่อนหน้า ถือว่าอยู่ในยอดนั้นแล้ว จึงไม่หักอีก แก้หรือลบรายการเก่าก็ไม่ทำให้ยอดที่ปรับแล้วเพี้ยน

**ขึ้นรอบใหม่:** เมื่อถึงวันรับเงิน (วันที่เหลือ ≤ 0) ผู้ใช้ตั้งรอบใหม่ รอบเก่าเปลี่ยนเป็น closed แผนที่ยังเป็น "วางแผน" ย้ายตามไปรอบใหม่ (ผมตัดสินใจเอง)

### การจัดการตัวเลข (ผมตัดสินใจเอง)

- เก็บเงินเป็น **สตางค์ (จำนวนเต็ม)** ไม่ใช้ทศนิยม กันเศษปัดผิด
- งบต่อวันแสดงเป็นบาทเต็ม **ปัดลง** ให้ผู้ใช้ไม่เห็นเงินมากกว่าที่มีจริง
- ตัวคำนวณเป็นฟังก์ชันล้วนใน `lib/calc/` ไม่แตะฐานข้อมูล รับข้อมูลเข้าแล้วคืนผล จึงเทสต์ได้ครบด้วย Vitest

## 6. ข้อมูลที่เก็บ (การ์ด 05)

หลักการ: **ไม่เก็บค่าที่คำนวณได้** เช่น ไม่มีคอลัมน์ "ยอดคงเหลือ" เพราะเงินจริง = เงินตั้งต้น − ผลรวมรายจ่าย ถ้าเก็บซ้ำสองที่ วันหนึ่งจะไม่ตรงกัน

### ชั้น 0–1

| ตาราง | คอลัมน์หลัก | หมายเหตุ |
|---|---|---|
| `users` | `id`, `line_user_id` (unique), `created_at` | สร้างครั้งแรกที่ตรวจ token ผ่าน |
| `cycles` | `id`, `user_id`, `start_balance`, `start_balance_at`, `payday` (date), `emergency_buffer`, `savings_amount`, `savings_percent`, `essential_food_daily`, `essential_transport_daily`, `income_source` (family/side_job/other), `income_frequency` (weekly/monthly/irregular), `status` (active/closed), `version`, `started_at` | ผู้ใช้มีรอบ active ได้รอบเดียว · วันที่ในเดือน/วันในสัปดาห์ของเงินเข้าอ่านจาก `payday` ไม่เก็บซ้ำ · `savings_amount` ตรึงตอนตั้งรอบ `savings_percent` แค่บอกว่าเลือกแบบ % (null = กรอกเอง) · `version` เพิ่มทุกครั้งที่แก้ ใช้ปฏิเสธหน้าจอที่ถือข้อมูลเก่า (การ์ด 23) |
| `balance_checks` | `id`, `user_id`, `cycle_id`, `balance`, `as_of`, `created_at` | ประวัติ "ปรับยอด" ล่าสุดตาม `as_of` คือยอดอ้างอิง |
| `entries` | `id`, `user_id`, `cycle_id`, `amount`, `category`, `note`, `spent_on` (date), `source` (chat/form/plan/reminder/ocr), `idempotency_key` (unique), `created_at`, `updated_at` | รายจ่ายจริง แก้และลบได้ |
| `plans` | `id`, `user_id`, `cycle_id`, `kind` (bill/purchase), `title`, `amount`, `due_on`, `status` (reserved/paid/cancelled/separate), `entry_id` (unique), `version` | บิลค้างและแผนซื้อ จ่ายแล้วจะชี้ไปที่รายจ่ายที่สร้าง (รายจ่ายหนึ่งปิดได้แผนเดียว) · `separate` = บิลจ่ายแยก ไม่หัก (เฉพาะ bill) · บิลที่จ่ายก่อนกรอกยอด = `paid` ไม่มี entry |
| `category_limits` | `cycle_id`, `category`, `amount` | วงเงินต่อหมวด (ถ้าผู้ใช้ตั้ง) |
| `chat_drafts` | `id`, `user_id`, `payload` (jsonb), `status` (pending/confirmed/discarded), `expires_at` | รายการร่างจากแชต รอกดยืนยัน |
| `line_events` | `webhook_event_id` (PK), `received_at` | กัน event ซ้ำจาก LINE |

หมวดผู้ใช้ 4 หมวดตาม Figma: อาหาร (`food`), เดินทาง (`transport`), ของใช้ (`supplies`), อื่นๆ (`other`) · หมวด `bills` ใช้เฉพาะรายจ่ายที่เกิดจากกด "จ่ายแล้ว" กับแผน (ฐานข้อมูลบังคับ `source = 'plan'`) เพื่อไม่ให้ค่าหอไปกองใน "อื่นๆ" (ทีมเลือก 11 พ.ย.) · วงเงินต่อหมวดตั้งได้เฉพาะ 4 หมวด ยังไม่ให้ผู้ใช้สร้างหมวดเอง

|---|---|
| `reminder_settings` | เปิด/ปิด และเวลาเตือนของผู้ใช้ |
| `reminder_log` | unique (`user_id`, `pattern_key`, `date`) → เตือนเรื่องเดิมวันละครั้ง และกดซ้ำบันทึกครั้งเดียว |
| `promos`, `redemptions` | โปรร้าน และการใช้สิทธิ์ (รหัส unique ใช้ได้ครั้งเดียว) |
| `points_ledger`, `rewards`, `reward_claims` | แต้มแบบบัญชีเพิ่ม/ลด (unique ต่อผู้ใช้ต่อวันไทย) และสต็อกที่หักใน transaction |

รูปแบบรายจ่ายที่เกิดซ้ำ **ไม่เก็บเป็นตาราง** คำนวณสดจากประวัติ `entries`

## 7. ตัวตน (การ์ด 06)

**จากหน้าจอ LIFF**
1. หน้าจอเรียก `liff.getIDToken()` แล้วส่งมาใน header `Authorization: Bearer <id token>`
2. server ส่ง token ไปตรวจที่ LINE (`POST https://api.line.me/oauth2/v2.1/verify` พร้อม channel ID ของ LINE Login channel ที่มี LIFF app)
3. ผ่าน → ได้ `sub` (LINE user ID) → หาหรือสร้างแถวใน `users`
4. ทุกคำสั่งที่อ่านหรือเขียนข้อมูลใช้ `user_id` จากขั้นนี้เท่านั้น **ไม่เชื่อ user ID ที่ส่งมาใน body หรือ URL**
5. token หมดอายุหรือไม่ผ่าน → ตอบ 401 หน้าจอขอ token ใหม่

**จากแชต (webhook)**
1. ตรวจ `x-line-signature` (HMAC-SHA256 ของ body ดิบด้วย channel secret) ไม่ตรง → ตอบ 401 และไม่ทำอะไร
2. ลายเซ็นตรง → เชื่อ `source.userId` ใน event ได้
3. บันทึก `webhookEventId` ลง `line_events` ก่อน ถ้าซ้ำ → ข้าม (LINE อาจส่ง event เดิมซ้ำ)

## 8. API ที่หน้าจอเรียก (ชั้น 0–1)

ทุกเส้นต้องมี ID token ทุกคำตอบที่มีตัวเลขเงินมาจากตัวคำนวณเดียวกัน

| เส้น | ทำอะไร |
|---|---|
| `GET /api/me` | ข้อมูลผู้ใช้ + มีรอบ active หรือยัง |
| `POST /api/cycle` | ตั้งรอบใหม่ (เงิน, วันรับเงิน, เงินเผื่อ, บิลค้าง) |
| `PATCH /api/cycle` | ปรับยอดเงิน, เลื่อนวันรับเงิน, ปรับเงินเผื่อ |
| `GET /api/summary` | งบต่อวัน, วันนี้เหลือ, เงินใช้ได้, ยอดขาด, ยอดรวมตามหมวดเทียบวงเงิน |
| `GET /api/entries` · `POST /api/entries` | ดูและเพิ่มรายจ่าย (POST ต้องมี header `Idempotency-Key`) |
| `PATCH /api/entries/:id` · `DELETE /api/entries/:id` | แก้/ลบ เฉพาะของเจ้าของ (ของคนอื่นตอบ 404 ไม่ใช่ 403 เพื่อไม่บอกว่ามีอยู่) |
| `POST /api/simulate` | ลองก่อนจ่าย: คืนผลคำนวณ ไม่บันทึกอะไร |
| `GET /api/plans` · `POST /api/plans` | ดูแผน / สร้างแผน (วางแผน) |
| `POST /api/plans/:id/pay` | จ่ายแล้ว: สร้างรายจ่ายและปลดยอดกันไว้ใน transaction เดียว กดซ้ำได้ผลเดิม |
| `POST /api/plans/:id/cancel` | ยกเลิกแผน |
| `PUT /api/category-limits` | ตั้งวงเงินต่อหมวดของรอบนี้ |

รูปแบบ error: `{ "error": { "code": "...", "message": "ข้อความไทยสำหรับผู้ใช้" } }`
รูปแบบ request/response ละเอียดจะตกลงกับโฟรวิวเป็นไฟล์ type ใน `lib/api-types.ts` ที่ทั้งสองฝั่ง import ร่วมกัน

## 9. ทางเข้าแชต (ชั้น 1) และการเตือน (ชั้น 2)

### จดผ่านแชต
1. ผู้ใช้พิมพ์ "ข้าว 45"
2. ตัวแยกแบบกฎหายอดเงินและเดาหมวดจากคำ (ชั้น 3 จะเพิ่ม AI เข้ามาก่อนกฎ ถ้า AI ล่มหรือช้าเกิน 5 วินาที ใช้กฎแทน)
3. สร้าง `chat_drafts` แล้ว reply: "อาหาร 45 บาท" พร้อมปุ่ม **[ยืนยัน] [แก้]**
4. กดยืนยัน → postback มี draft id → เปลี่ยนสถานะ pending → confirmed **เฉพาะแถวที่ยัง pending** แล้วสร้างรายจ่ายด้วย `idempotency_key = draft id` → reply "บันทึกแล้ว วันนี้เหลือ 105"
5. กดซ้ำ → draft ไม่ pending แล้ว → ตอบยอดล่าสุด ไม่บันทึกเพิ่ม
6. กดแก้ → เปิดหน้าฟอร์มใน LIFF ที่กรอกค่าร่างไว้แล้ว
7. พิมพ์แล้วแยกไม่ออก → ตอบพร้อมปุ่มเปิดฟอร์ม (ฟอร์มสำรองตามแผน)

### เตือนจากพฤติกรรม
- **กฎหาเรื่องที่เกิดซ้ำ:** หมวดเดียวกัน ยอดห่างกันไม่เกิน ±20% เกิดอย่างน้อย 3 วันใน 7 วันล่าสุด ในช่วงเวลาใกล้กัน (±90 นาที)
- **ตัวตั้งเวลา:** ใช้ Supabase Cron เรียก `POST /api/cron/reminders` ทุก 15 นาที พร้อม secret header (Vercel Hobby ทำไม่ได้ ดูข้อ 3) ⚠️ ต้องเช็กว่าแผนฟรีของ Supabase ใช้ได้
- **เงื่อนไขส่ง:** ผู้ใช้เปิดการเตือน · ถึงเวลาเตือนแล้ว · วันนี้ยังไม่มีรายการในหมวดนั้น · ยังไม่เคยเตือนเรื่องนี้วันนี้ · ไม่เกินวันละ 1 ข้อความต่อคน
- **ส่ง:** push พร้อมปุ่ม **[ใช่ จดเลย] [แก้ยอด] [วันนี้ไม่ได้ซื้อ]** ทุกปุ่มบันทึกผลใน `reminder_log` ครั้งเดียว
- **โควตา:** ผู้ทดลอง 15 คน × วันละ 1 × 5 วัน = 75 ข้อความ อยู่ในโควตาฟรีที่รายงานไว้
- **สำหรับเดโม:** มีเส้น `POST /api/cron/reminders?user=<ตัวเอง>&force=1` (ใช้ได้เฉพาะเมื่อตั้งค่า `DEMO_MODE`) ให้กดส่งการเตือนทันที ไม่ต้องรอเวลาจริง

## 10. ชั้น 3–7 (กรอบไว้ ยังไม่ละเอียด)

- **AI (ชั้น 3):** AI แปลงข้อความเป็นข้อมูลมีโครงสร้าง (structured output) → ตัวคำนวณคำนวณ → ส่งผลตัวเลขให้ AI อธิบายเป็นภาษาคน AI ห้ามสร้างตัวเลขเงินเอง ตัวเลขในคำตอบต้องมาจากผลคำนวณที่ส่งให้ ส่งข้อมูลเฉพาะที่จำเป็น ไม่ส่งชื่อหรือ LINE ID
- **OCR (ชั้น 4):** ดึงรูปจาก LINE content API → โมเดล AI ที่อ่านรูปได้ → ได้รายการร่าง → ใช้ flow ยืนยันเดียวกับแชต
- **โปร (ชั้น 5):** รหัสสุ่ม unique ต่อการกดรับ หน้าร้านยืนยันด้วย PIN ร้าน การยืนยันซ้ำได้ผลเดิม
- **แต้ม (ชั้น 6):** เช็กครบแล้ว 1 แต้มต่อวันไทย (unique) แลกของหักแต้มและสต็อกใน transaction เดียว
- **รายงานร้าน (ชั้น 7):** แสดงเฉพาะกลุ่มที่มีอย่างน้อย 5 คน กันการระบุตัวบุคคล
