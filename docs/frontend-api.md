# คู่มือเรียก API สำหรับหน้าจอ (ถึงโฟรวิว)

อัปเดต 12 พ.ย. 2569 (เพิ่ม `POST /api/cycle`) · เขียนโดย พอ (Backend) · branch `Backend` · ระบบจริง `https://porchai.vercel.app`

> สรุปสั้น: หน้าจอเรียก `/api/*` เท่านั้น ห้ามต่อ Supabase ตรง · ทุกคำขอต้องแนบ ID token ของ LINE · **เงินเป็นสตางค์** · ค่าที่เป็น `null` แปลว่า "ยังไม่รู้" ห้ามแสดงเป็น 0

---

## 1. กติกา 5 ข้อที่ต้องรู้ก่อน

1. **เงินเป็นสตางค์จำนวนเต็มทุกช่อง** `4500` = 45 บาท
   - แสดงผล: `amount / 100`
   - ส่งเข้า: ผู้ใช้พิมพ์ 45 → ส่ง `4500` (ต้องเป็นจำนวนเต็ม > 0)
2. **วันที่** เป็น `YYYY-MM-DD` ตามเวลาไทย · เวลา (`balanceAsOf`, `createdAt`) เป็น ISO
3. **`null` = ยังไม่รู้ ต้องถามผู้ใช้** ห้ามแสดงเป็น 0 (ดูข้อ 5)
4. **ตัวเลขเงินทุกตัวมาจาก server** ห้ามคำนวณงบเองในหน้าจอ แชต หน้าจอ และ AI ต้องได้ตัวเลขเดียวกัน
5. **ชนิดข้อมูลทั้งหมดอยู่ใน `lib/api-types.ts`** import ไปใช้ได้เลย

## 2. เข้าระบบ (LIFF)

- LIFF ID อยู่ที่ `lib/liff/config.ts` (`2012545176-udYyTUiA`)
- `app/layout.tsx` มี `LiffStateRedirect` อยู่แล้ว: ลิงก์ `liff.line.me/<id>/หน้าไหนก็ได้` จะพาไปหน้านั้นเอง **อย่าลบออกจาก layout**
- channel PorChai Login เป็น **Published** แล้ว ทุกบัญชี LINE เปิดได้

ขั้นตอนในหน้าจอ (ดูตัวอย่างที่ใช้ได้จริงใน `app/dev/liff-check/page.tsx`)

```ts
const liff = (await import("@line/liff")).default; // import ใน useEffect เท่านั้น (ใช้ window)
await liff.init({ liffId: LIFF_ID });
if (!liff.isLoggedIn()) { liff.login({ redirectUri: window.location.href }); return; }
const token = liff.getIDToken();

await fetch("/api/summary", { headers: { Authorization: `Bearer ${token}` } });
```

- ได้ **401** → token หมดอายุหรือไม่ถูกต้อง ให้ขอ token ใหม่ (init/login ใหม่)
- server ไม่เชื่อ userId ที่ส่งมา ไม่ต้องส่ง userId ไปเลย

### 3.1 ตั้งรอบเงิน (`POST /api/cycle`) — หน้า W4–W9 ส่งครั้งเดียวตอนกด "เริ่มใช้" (W9)

```json
{
  "incomeSource": "family",
  "incomeFrequency": "monthly",
  "payday": "2026-11-23",
  "balance": 240000,
  "balanceAsOf": "2026-11-11T01:10:00Z",
  "bills": [
    { "title": "ค่าหอ", "amount": 60000, "dueOn": "2026-11-15", "status": "unpaid" }
  ],
  "savingsPercent": 10,
  "emergencyBuffer": 12000,
  "essentials": { "food": 5000, "transport": 2000 },
  "flexibleItems": [
    { "title": "ทริป", "amount": 50000, "dueOn": "2026-11-20" }
  ]
}
```

| ช่อง | หน้า | ต้องใส่ไหม | กติกา |
|---|---|---|---|
| `incomeSource` | W4 | ✅ | `family` เงินจากบ้าน/ทุน · `side_job` งานพิเศษ · `other` อื่น ๆ |
| `incomeFrequency` | W4 | ✅ | `weekly` รายสัปดาห์ · `monthly` รายเดือน · `irregular` ไม่แน่นอน |
| `payday` | W4 | ✅ | วันที่ผู้ใช้เลือก ต้องหลังวันนี้ (ถ้าเลือกวันนี้ = ถามว่าเงินเข้าแล้วหรือยัง) · ระบบอ่าน "ทุกวันที่ X" จากวันนี้เอง ไม่ต้องส่งแยก |
| `balance` | W5 | ✅ | เงินที่มี (สตางค์) |
| `balanceAsOf` | W5 "แก้เวลา" | ไม่ต้อง | เวลาที่ยอดนั้นจริง ไม่ส่ง = ตอนกดบันทึก · ห้ามเป็นอนาคต |
| `bills[]` | W5 | ไม่ต้อง | ไม่เกิน 20 · `status`: `unpaid` (ค่าเริ่มต้น กันเงินไว้) · `paid` จ่ายแล้ว (ไม่หักซ้ำ) · `separate` จ่ายแยก (ไม่หัก) |
| `savingsPercent` **หรือ** `savingsAmount` | W6 | ไม่ต้อง | เลือกอย่างเดียว · % = 1–100 คิดจาก `balance` (10% ของ 2,400 = 240) · บาท = สตางค์ |
| `emergencyBuffer` | W6 | ไม่ต้อง (0) | ออม + เผื่อ ห้ามเกิน `balance` |
| `essentials` | W7 | ไม่ต้อง | ใส่ `food` + `transport` คู่กัน · **ไม่ใส่ = ยังไม่รู้** (ซื้อได้ไม่เกินจะเป็น `null` ข้อ 5) |
| `flexibleItems[]` | W8 | ไม่ต้อง | ไม่เกิน 20 · ถ้า `dueOn` หลังวันเงินเข้า = รอบหน้า ไม่หักรอบนี้ |

- ส่ง Figma ชุดข้างบน (ไม่มี `flexibleItems`) → `summary.budget.dailyBudget` = 12000 (120/วัน) · `maxPurchase` = 60000 (600) · `dailyBudget` ปัดลงเป็นขั้น 25 สตางค์ (233.33 → 233.25)
- ตั้งรอบได้ทีละรอบ: มีรอบที่ยังไม่ถึงวันเงินเข้าอยู่แล้ว → 409 `cycle_exists` · ถึงวันเงินเข้าแล้วตั้งใหม่ได้ (รอบเก่าปิด บิล/รายการที่ยังไม่จ่ายย้ายมารอบใหม่)
- ส่งซ้ำ (กดสองที) ได้รอบเดียว ครั้งที่สองได้ 409 `cycle_exists` → ไปหน้าหลักได้เลย

### จดรายจ่าย (`POST /api/entries`)

```json
{ "amount": 4500, "category": "food", "note": "ข้าว", "spentOn": "2026-11-11" }
```

- `category` เลือกได้ 4 หมวด: `food` อาหาร · `transport` เดินทาง · `supplies` ของใช้ · `other` อื่น ๆ
- `spentOn` ไม่ส่ง = วันนี้ · ห้ามเป็นวันในอนาคต
- `note` ไม่เกิน 200 ตัวอักษร
- **header `Idempotency-Key`**: สร้างใหม่ 1 ค่าต่อ 1 การกดบันทึก (เช่น `crypto.randomUUID()`) ถ้าเน็ตหลุดแล้วส่งซ้ำ **ใช้ค่าเดิม** server จะบันทึกครั้งเดียว (ส่งซ้ำได้ `200` + รายการเดิม) ถ้ากดบันทึกรายการใหม่ ต้องสร้างค่าใหม่

### 3.2 แผน (`/api/plans`) — หน้า W15 ตัดสินใจต่อ · W16 แผนของฉัน · L8 (การ์ด 57)

ปุ่มบน W15 ใช้ API แบบนี้:

| ปุ่ม W15 | เรียก | เงินจริง | ยอดกันไว้ |
|---|---|---|---|
| ยืนยันจ่ายจริง (ยังไม่เคยเก็บในแผน) | `POST /api/entries` ตามปกติ | ลด | ไม่เปลี่ยน |
| เก็บไว้ในแผน | `POST /api/plans` `{ title, amount }` | ไม่เปลี่ยน | เพิ่ม |
| เลื่อนไปรอบหน้า | `POST /api/plans` `{ title, amount, status: "postponed" }` | ไม่เปลี่ยน | ไม่เปลี่ยน (ไปนับรอบหน้า) |
| ยกเลิก (ปุ่มล่าง) | ไม่ต้องเรียกอะไร | – | – |

ปุ่มของแผนที่บันทึกแล้ว (W16):

| ปุ่ม | เรียก | ทำได้เมื่อสถานะเป็น | ผล |
|---|---|---|---|
| จ่ายแล้ว | `/pay` | `reserved`, `postponed` | เงินจริงลด 1 ครั้ง ยอดกันปลด สร้างรายจ่าย `source: "plan"` |
| ยกเลิกการจ่าย | `/unpay` | `paid` | รายจ่ายนั้นถูกยกเลิก (ไม่ลบ) แผนกลับไปเป็น `reserved` |
| ยกเลิก | `/cancel` | `reserved`, `postponed` | ปลดยอดกันอย่างเดียว ไม่มีรายรับปลอม |
| เลื่อน | `/postpone` | `reserved` | ไม่นับในรอบนี้ |
| เก็บไว้ในแผน | `/keep` | `postponed` | กลับมานับเป็นยอดกัน |

**แนะนำการวางปุ่ม** (API รองรับ 5 อย่าง แต่ไม่ต้องโชว์พร้อมกัน — โชว์เฉพาะที่กดได้ตามสถานะ):

| สถานะแผน | ปุ่มที่เห็นเลย | ซ่อนในเมนู "แก้แผน" (W16) | เกิดบ่อยไหม |
|---|---|---|---|
| `reserved` เก็บไว้ในแผน | **จ่ายแล้ว** | เลื่อน · ยกเลิก | บ่อย |
| `postponed` เลื่อนไปรอบหน้า | ไม่มี (ป้าย "เลื่อน" แบบ W16) | เก็บไว้ในแผน · ยกเลิก | น้อย |
| `paid` จ่ายแล้ว | ไม่มี | ยกเลิกการจ่าย | น้อยมาก (กดผิด) |
| `cancelled` / `separate` | ไม่มี | – | – |

"ยกเลิกการจ่าย" อย่าวางข้างปุ่ม "จ่ายแล้ว" (จะดูเหมือนให้เลือกระหว่างสองอย่าง) ให้อยู่ในเมนูหรือหน้ารายละเอียดของรายการที่จ่ายแล้วเท่านั้น

- **กดซ้ำ / เปิดสองหน้าจอ / เน็ตหลุดแล้วส่งซ้ำ ได้ผลเดิม** ไม่หักเงินซ้ำ (กดจ่ายสองที → เงินลดครั้งเดียว ได้ `entryId` เดิม) ยกเว้นทำไม่ได้จากสถานะปัจจุบัน → 409 `plan_status` แสดง `message` ได้เลย (เช่น จ่ายกับยกเลิกพร้อมกัน อันหนึ่งได้ 409)
- `POST /api/plans` ต้องมี header `Idempotency-Key` แบบเดียวกับจดรายจ่าย
- `category` (`food`/`transport`/`supplies`/`other`) ส่งได้ตอนเก็บแผน หรือตอนกดจ่าย (ตอนจ่ายมีผลกว่า) ไม่ส่งเลย = `other` · บิลเข้าหมวด `bills` เสมอ (ส่ง `category` กับบิลตอนสร้าง → 422)
- `plan.heldThisCycle` = แผนนี้นับอยู่ใน `summary.reserved` ตอนนี้ไหม (false ถ้าเลื่อน / ครบกำหนดหลังวันเงินเข้า / จ่ายแล้ว / ยกเลิก)
- แผนที่เลื่อนไว้ พอตั้งรอบใหม่จะย้ายตามไปและกลายเป็น "เก็บไว้ในแผน" ของรอบใหม่
- ยังไม่มีการนับ "ใช้สิทธิ์แผนฟรี 3/3" ใน W16 (รอทีมตกลง)
- ตัวอย่างกลาง 1,000: เก็บค่าอุปกรณ์ 250 → `balance` 100000, `reserved` 25000 · จ่ายแล้ว → `balance` 75000, `reserved` 0 งบต่อวันเท่าเดิม

### 3.3 ลองก่อนจ่าย (`POST /api/simulate`) — W11–W14, L4–L5 (การ์ด 14)

**ไม่บันทึกอะไรเลย** กดลองกี่ครั้งก็ได้ ยอดเงินกับแผนไม่เปลี่ยน (มีเทสต์ยืนยัน)

```json
{ "amount": 48000 }
```

| ช่อง | ใช้เมื่อ |
|---|---|
| `amount` | ราคาของที่จะลอง (W11) |
| `postponePlanIds` | ลองเลื่อนแผนที่กันเงินอยู่ เช่น "ถ้าเลื่อนค่ากิจกรรม 200 ล่ะ?" (ส่ง id จาก `GET /api/plans`) · ส่งคู่กับ `amount` ก็ได้ |
| `dueOn` | ของที่จะซื้อหลังวันเงินเข้า → `countsThisCycle: false` ผลไม่เปลี่ยน |
| `payday` | ลองเลื่อนวันเงินเข้า (หลังวันนี้) เช่น "เงินเข้าช้า 2 วัน" (การ์ด 23) |
| `balance` | ลองยอดเงินจริงใหม่ก่อนกดปรับยอด (การ์ด 23) |
| `emergencyBuffer` | ลองเงินเผื่อค่าใหม่ เช่น "ถ้าใช้เงินเผื่อ 120 ซื้อหูฟัง" → `{ amount: 70000, emergencyBuffer: 0 }` (การ์ด 19) |
| `essentials` | คำตอบ "ค่ากิน + ค่ารถต่อวันเท่าไร" ที่เพิ่งถาม ใช้กับการลองครั้งนี้เท่านั้น (ถ้าจะจำไว้ เรียก `PUT /api/cycle/essentials` ด้วย) |

ต้องมีอย่างน้อยหนึ่งอย่าง: `amount`, `postponePlanIds`, `emergencyBuffer`, `payday` หรือ `balance` · ทุกคำตอบมี `basis` (ข้อ 3.5)

**ได้อะไรกลับ → ไปอยู่ตรงไหนใน Figma**

| ช่อง | ตัวอย่าง W12 รองเท้า 480 | W14 หูฟัง 700 |
|---|---|---|
| `before.dailyBudget` / `before.maxPurchase` | "ตอนนี้ 120 บาท/วัน · ซื้อได้ไม่เกิน 600" | เหมือนกัน |
| `after.dailyBudget` | ซื้อทันที **80** บาท/วัน | **6150** → 61.50 บาท/วัน (Figma เขียน 61) |
| ไม่ซื้อ / เลื่อน | ใช้ `before.dailyBudget` (120) | 120 |
| `overLimitBy` | 0 | **10000** → "เกินวงเงิน 100" |
| `after.essentialShortPerDay` | 0 | 850 → "ขาดวันละ 8.50" |
| `checks.bills` + `billsCovered` | "บิล 600 ยังพอ" ✓ | ✓ |
| `checks.essentialPerDay` + `essentialsCovered` | "ค่าจำเป็น 70/วัน ยังพอ" ✓ | ⚠ ไม่พอ |
| `checks.savings` / `emergencyBuffer` | "เงินออม 240 · เงินเผื่อ 120 ไม่ถูกแตะ" | เหมือนกัน (ลองไม่เคยดึงมาใช้) |
| `checks.otherPlans` | "แผนอื่นรอบนี้" (ยอดของที่กันไว้อื่น) | |

**`verdict` มี 4 แบบ ต้องรองรับทุกแบบ**

| `verdict` | ความหมาย | หน้าจอ |
|---|---|---|
| `ok` | ซื้อได้ ค่ากินค่ารถยังพอทุกวัน | W12 |
| `essentials_short` | จ่ายได้ แต่งบต่อวันต่ำกว่าค่ากินค่ารถ | W14 เกินวงเงิน |
| `shortfall` | เงินไม่พอแม้แต่บิล/ออม/เผื่อ (`after.shortfall` = ขาดเท่าไร) | บอกส่วนที่ขาด |
| `ask` | ต้องถามก่อน ดู `needs` · `before`/`after`/`checks` เป็น `null` | ถามแล้วลองใหม่ |

`needs`:
- `"essentials"` → ถาม "ค่ากิน + ค่ารถต่อวันเท่าไร?" แล้วส่งมาใน `essentials` ของการลองครั้งถัดไป และ/หรือบันทึกด้วย `PUT /api/cycle/essentials`
- `"payday"` → วันนี้ถึงวันเงินเข้าแล้ว ถามว่าเงินเข้าหรือยัง ถ้าเข้าแล้ว พาไปตั้งรอบใหม่ (`POST /api/cycle`)

**ยังไม่มี: "ลองล่าสุด" (ชิป W11/W13)** ทีมยังไม่ได้ตัดสินว่าจะเก็บที่ไหน (ในเครื่องหรือ backend) ทำหน้าจอไปก่อนได้โดยไม่มีชิป

### 3.4 เงินเผื่อ — ปุ่ม "ปรับ ›" ของ "เงินออม + เงินเผื่อรอบนี้" (W10) (การ์ด 19)

ใช้บางส่วน หรือกันเพิ่ม **เงินจริงไม่เปลี่ยน** เปลี่ยนแค่เงินที่ใช้วางแผนได้

1. **หน้าสรุป (ยังไม่บันทึก):** `POST /api/simulate` `{ "emergencyBuffer": 0 }` → แสดง `before.dailyBudget` → `after.dailyBudget` (Figma: 120 → 130/วัน) พร้อมปุ่ม ยืนยัน / ยกเลิก
2. **ยืนยัน:** `PUT /api/cycle/buffer` `{ "amount": 0, "previous": 12000 }`
   - `amount` = เงินเผื่อค่าใหม่ (ไม่ใช่จำนวนที่จะลด) → กดซ้ำได้ผลเดิม ไม่หักซ้ำ
   - `previous` = เงินเผื่อที่หน้าสรุปแสดงอยู่ (`summary.emergencyBuffer`) ถ้ามีอีกหน้าจอเปลี่ยนไปก่อน → 409 `stale` ให้โหลดใหม่แล้วให้ผู้ใช้ดูสรุปอีกรอบ
   - `summary` ที่ได้กลับ ตัวเลขตรงกับ `after` ของหน้าสรุป (มีเทสต์)
3. **ยกเลิก:** ไม่ต้องเรียกอะไร ค่าเดิมอยู่เหมือนเดิม
4. เงินออม + เงินเผื่อ ต้องไม่เกินเงินที่มีตอนนี้ → 422 "เงินออมรวมเงินเผื่อเกินเงินที่มี"

⚠ ข้อความใต้การ์ด W10 "ถ้าใช้เงินเผื่อไปแล้ว กด ปรับยอด" — ถ้าผู้ใช้ปรับยอดอย่างเดียว เงินเผื่อยังถูกกัน 120 อยู่ เงินที่หายไปจะไปลดงบใช้จ่ายแทน (เหมือนไม่ได้ใช้เงินเผื่อ) แนะนำเปลี่ยนเป็น "ถ้าใช้เงินเผื่อไปแล้ว: ลดเงินเผื่อ (ปรับ ›) แล้วจดรายจ่าย"

### 3.6 AI แนะนำก่อนจ่าย (`POST /api/advice`) — หน้าคำแนะนำ (การ์ด 15)

```json
{ "question": "พรุ่งนี้กินชาบู 300 บาทไหวไหม" }
```

ได้ `Advice` (ชนิดอยู่ใน `lib/api-types.ts`):

| ช่อง | ใช้ทำอะไร |
|---|---|
| `verdict` | `enough` เงินพอ · `tight` เงินตึง (จ่ายได้ แต่งบต่อวันต่ำกว่าค่ากินค่ารถ) · `short` เงินไม่พอ · `ask` ข้อมูลไม่ครบ |
| `needs` | ตอน `ask`: `amount` (ไม่มีราคา) · `essentials` (ยังไม่ตั้งค่ากินค่ารถ → `PUT /api/cycle/essentials`) · `payday` |
| `item`, `amount`, `dueOn`, `category` | สิ่งที่อ่านได้จากคำถาม (`dueOn` null = วันนี้) |
| `before` / `after` | ผลคำนวณก่อน/หลัง แบบเดียวกับลองก่อนจ่าย |
| `options` | ทางเลือก: `spend_less { maxAmount }` ลดงบ · `postpone { plans, after }` เลื่อนแผน · `use_buffer { buffer, after }` ใช้เงินเผื่อ (ต้องให้ผู้ใช้อนุญาต → `PUT /api/cycle/buffer`) |
| `explanation` | ข้อความพร้อมแสดง (ภาษาไทย) |
| `byAI` | `true` = AI เขียน (ผ่านการตรวจตัวเลขแล้ว) · `false` = ข้อความแม่แบบ |
| `basis` | ส่งต่อตอนยืนยัน (ข้อ 3.5) |

ยืนยันหลังดูผล: จ่ายเลย → `POST /api/entries` · เก็บไว้ในแผน → `POST /api/plans { title: item, amount, dueOn, category, basis }` · ไม่ทำอะไร = ยกเลิก
ในแชต พิมพ์คำถามแบบเดียวกัน (มี ไหวไหม / พอไหม / ได้ไหม / ?) บอทตอบพร้อมปุ่ม ยืนยันจ่ายจริง / เก็บไว้ในแผน

**แชตคุยกับ AI (ฝั่งแชตอย่างเดียว ไม่มี API ใหม่ให้หน้าจอ):** ทักทาย / «เหลือกี่บาท?» / «ข้าว» แล้วตอบยอด / «45» แล้วตอบชื่อ / หลายยอดในข้อความเดียว → ปุ่ม จดทั้งหมด / ไม่ใช่ · รายการที่จดจากแชตยังเป็น `source: "chat"` เหมือนเดิม · ⚠️ หน้ายินยอม W1–W3 ควรเพิ่ม: ข้อความแชตเก็บ 30 นาที และส่งให้ Google (Gemini) ประมวลผล

### 3.7 การเตือนรายการประจำ (`/api/reminders`) — แอป › ตั้งค่า › การเตือน (การ์ด 58)

`GET /api/reminders` → `{ enabled, time: "12:30", pausedUntil: "YYYY-MM-DD" | null, habits: [{ id, label, amount, time }] }` · `PUT /api/reminders { enabled, time: "HH:mm", pausedUntil }` → ค่าใหม่ (422 ถ้าเวลา/วันที่ผิด) · ค่าเริ่มต้นปิด · `habits` = รายการที่ระบบตรวจพบ (ชื่อเดียวกัน ≥ 3 วันใน 7 วัน) · ต่อใน `lib/client/live.ts` แล้ว · รายการที่จดจากปุ่มเตือนมี `source: "reminder"`

### รายจ่ายที่มาจากการจ่ายแผน (`source: "plan"`)

- **เปลี่ยนหมวดได้** ด้วย `PATCH /api/entries/:id` `{ category }` (L9) ยกเว้นรายจ่ายบิล (`bills`)
- แก้ยอด/วันที่/บันทึก หรือยกเลิกผ่าน `/api/entries` ไม่ได้ (409 `plan_entry`) → ใช้ `/api/plans/:id/unpay` แทน
- รายจ่ายบิลมี `category: "bills"` ใช้เฉพาะรายการแบบนี้

### 3.5 ปรับแผน — เงินเข้าช้า / มีรายจ่ายเพิ่ม / แก้ยอด (การ์ด 23)

ทุกกรณีใช้แบบเดียวกัน: **ลอง (ดูก่อน/หลัง) → ยืนยัน หรือ ยกเลิก (ไม่ต้องเรียกอะไร)**

| เหตุการณ์ | ดูก่อน/หลัง | ยืนยัน |
|---|---|---|
| เงินเข้าช้า (หรือเร็วขึ้น) | `POST /api/simulate { payday }` | `PUT /api/cycle/payday { payday, basis }` |
| มีรายจ่ายเพิ่ม | `POST /api/simulate { amount }` | `POST /api/plans { title, amount, basis }` (+ `Idempotency-Key`) |
| แก้ยอดเงิน | `POST /api/simulate { balance }` | `POST /api/cycle/balance { balance, basis }` |

**`basis` คืออะไร:** รหัสสั้นๆ ที่บอกว่าผลคำนวณนี้มาจากตัวเลขชุดไหน (มีใน `summary.basis` และในคำตอบของ simulate) ตอนกดยืนยันให้ส่ง `basis` ที่ได้จากหน้าสรุปกลับมา ถ้าระหว่างนั้นมีอะไรเปลี่ยน เช่น จดรายจ่ายจากแชต แผนเปลี่ยน หรือข้ามวัน → ได้ **409 `stale`** ให้เรียก simulate ใหม่แล้วให้ผู้ใช้ดูผลอีกรอบก่อนยืนยัน (เกณฑ์ "แผนเก่าที่ข้อมูลเปลี่ยนต้องคำนวณใหม่ก่อนยืนยัน")
- `PUT /api/cycle/payday` ต้องมี `basis` เสมอ · ใน `plans` กับ `cycle/balance` ส่งหรือไม่ส่งก็ได้ (ถ้าส่งจะเช็กให้)
- กดยืนยันซ้ำ: วันเงินเข้า → ได้ผลเดิม · แผน → ได้แผนเดิม (ตาม `Idempotency-Key`) · ปรับยอด → ครั้งที่สองอาจได้ 409 เพราะตัวเลขเปลี่ยนแล้ว ให้ปิดปุ่มหลังกดครั้งแรก

**ตัวอย่างกลาง 1,000 (เหลือเผื่อ 50) → เงินเข้าช้า 2 วัน:** `before.spare` = 5000 → `after.spare` = −9000 (ค่ากินค่ารถเพิ่ม 70 × 2 = 140 → ขาด 90) · `after.daysLeft` 10 → 12 · ยืนยันแล้ว `summary.budget` ตรงกับ `after` · เงินจริงไม่เปลี่ยน ระบบไม่เดาว่าเงินใหม่เข้าแล้ว
- ค่าจำเป็นที่เพิ่ม = `essentialPerDay × (after.daysLeft − before.daysLeft)`
- แผนที่ครบกำหนดระหว่างวันเงินเข้าเก่ากับใหม่ จะถูกนับเข้ารอบนี้ด้วย (ทั้งตอนลองและหลังยืนยัน)

**งบต่อวันมีเศษสตางค์ได้ (R3-quarter, 13 พ.ย.):** `dailyBudget` ปัดลงทีละ 25 สตางค์ เช่น 23325 = 233.25 บาท ใช้ `formatBaht` แสดง (ได้ "233.25" · บาทเต็มไม่มีจุด) ห้ามปัดเองในหน้าจอ

## 4. `Summary` — แต่ละช่องไปอยู่ตรงไหนใน Figma

| ช่อง | ความหมาย | Figma (W10 / L2) |
|---|---|---|
| `budget.todayRemaining` | เหลือใช้ได้วันนี้ (ติดลบได้ = เกินงบ) | "เหลือใช้ได้วันนี้ 75" |
| `budget.dailyBudget` | งบวันนี้ (คงที่ทั้งวัน) | "งบวันนี้ 120" |
| `spentToday` | ใช้ไปแล้ววันนี้ | "ใช้ไปแล้ว 45" |
| `balance` | เงินที่มีตอนนี้ | "เงินที่มี 2,355" |
| `reserved` | บิล + แผนที่กันไว้ (ที่ครบกำหนดก่อนวันเงินเข้า) | "บิล 600" |
| `savings` · `emergencyBuffer` | เงินออม · เงินเผื่อ (หักตั้งแต่ต้นรอบ) | "ออม 240 · เผื่อ 120" |
| `budget.daysLeft` | วันที่เหลือถึงวันเงินเข้า (นับวันนี้) | "อีก 12 วันเงินเข้า" |
| `balanceAsOf` | เวลาของยอดเงินล่าสุด | "UpdatedAt" |
| `budget.maxPurchase` | ซื้อของชิ้นเดียวได้ไม่เกิน | "ซื้อได้ไม่เกิน 600" (W11–W14) |
| `budget.spare` | เงินเหลือหลังกันค่ากินค่ารถถึงวันเงินเข้า (ติดลบ = ขาด) | – |
| `budget.essentialShortPerDay` | งบต่อวันต่ำกว่าค่ากินค่ารถวันละเท่าไร | "ขาดวันละ 9" (W14) |
| `essentialPerDay` | ค่ากิน + ค่ารถต่อวันที่ผู้ใช้ตั้ง | "ค่าจำเป็นที่คุณตั้งไว้ 70" |

### `budget.kind` มี 3 แบบ ต้องรองรับทุกแบบ

| `kind` | เกิดเมื่อ | หน้าจอควรทำ |
|---|---|---|
| `"ok"` | ปกติ | แสดงตามตารางข้างบน |
| `"shortfall"` | เงินที่มีไม่พอแม้แต่ส่วนที่กันไว้ (บิล + แผน + ออม + เผื่อ) (`shortfall` = ขาดกี่สตางค์) | แสดงยอดขาด **ห้ามแสดงงบต่อวัน** |
| `"payday-passed"` | ถึง/เลยวันเงินเข้าแล้ว | ไม่มีงบต่อวัน → **ถามว่าเงินเข้าแล้วหรือยัง** แล้วตั้งรอบใหม่ |

ตอน `kind` ไม่ใช่ `"ok"` จะไม่มีช่อง `dailyBudget`, `todayRemaining`, `maxPurchase` ฯลฯ

## 5. ค่า `null` = ยังไม่รู้ → ถาม ห้ามแสดง 0

ถ้าผู้ใช้ยังไม่ได้ตั้งค่ากิน + ค่ารถต่อวัน (W7):

- `essentialPerDay` = `null`
- `budget.spare`, `budget.maxPurchase`, `budget.essentialShortPerDay` = `null`
- **"ใช้ได้วันละ" ยังแสดงตามปกติ** (เงินใช้ได้ ÷ วัน)

| สถานะ | ใช้ได้วันละ | ซื้อได้ไม่เกิน |
|---|---|---|
| ยังไม่ตั้งค่ากินค่ารถ | 75 | **ห้ามแสดง 0 หรือ 750** → ปุ่ม/คำถาม "ค่ากิน + ค่ารถต่อวันเท่าไร?" แล้วบันทึกด้วย `PUT /api/cycle/essentials` |
| ตั้ง 70/วัน | 75 | 50 |
| ผู้ใช้บอกว่าไม่มีเลย (ตั้ง 0) | 75 | 750 |

เหตุผล (การ์ด 14): ถ้าเดาเป็น 0 จะกลายเป็นบอกว่าเงินทั้งก้อนซื้อของเพิ่มได้ ทั้งที่ยังต้องกินข้าวอีก 10 วัน

## 6. Error

รูปแบบเดียวทุกเส้น: `{ "error": { "code": "...", "message": "ข้อความไทยพร้อมแสดงผู้ใช้" } }` แสดง `message` ได้เลย

| status | `code` | เมื่อไร |
|---|---|---|
| 400 | `bad_request` | body ไม่ใช่ JSON |
| 400 | `missing_idempotency_key` | จดรายจ่าย/เก็บแผนแต่ไม่ส่ง `Idempotency-Key` |
| 401 | `unauthorized` | ไม่มี token / token ไม่ผ่าน → ขอ token ใหม่ |
| 404 | `not_found` | ไม่พบรายการ/แผน (หรือเป็นของคนอื่น หรือปุ่มแผนที่ไม่มี) |
| 409 | `no_cycle` | ยังไม่ได้ตั้งรอบเงิน → พาไปหน้าตั้งค่า (W4–W9) |
| 409 | `cycle_exists` | ตั้งรอบซ้ำ ทั้งที่รอบเดิมยังไม่ถึงวันเงินเข้า |
| 409 | `entry_cancelled` | แก้รายการที่ยกเลิกแล้ว |
| 409 | `plan_entry` | แก้ยอด/ยกเลิกรายการที่มาจากการจ่ายแผน (เปลี่ยนหมวดได้) |
| 409 | `stale` | ตัวเลขเปลี่ยนไปแล้วระหว่างดูสรุป (`basis` ไม่ตรง / เงินเผื่อถูกเปลี่ยนจากอีกหน้าจอ) → เรียก simulate ใหม่แล้วให้ผู้ใช้ดูอีกรอบ |
| 409 | `plan_status` | ปุ่มของแผนทำไม่ได้จากสถานะตอนนี้ (เช่น ยกเลิกแผนที่จ่ายแล้ว) |
| 422 | `invalid_input` | ข้อมูลไม่ผ่าน (ยอด ≤ 0, หมวดผิด, วันที่อนาคต ฯลฯ) |
| 503 | `line_unavailable` | ต่อ LINE ไม่ได้ ลองใหม่ |
| 500 | `internal` | ระบบผิดพลาด |
